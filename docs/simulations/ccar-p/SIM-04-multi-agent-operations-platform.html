CCAR-P SIM-04 — Multi-Agent Operations Platform

How to use this: read the scene, then work through the decisions on paper, or paste the scene and the decisions list (not the answer key) into Claude and ask it to run the simulation one decision at a time with no hints. Open the coach key only when you've finished.

Primary domains: 1 Solution Design & Architecture, 2 Claude Models, Prompting & Context Engineering, 4 Evaluation, Testing & Optimization, 3 Integration · Decisions: 10 · Time: 20 min

Scene (original, written from the official objectives)

A logistics company wants Claude across operations. There are three needs: sort inbound shipment-exception emails into fixed categories within five minutes, investigate complex delayed shipments across tracking, warehouse and carrier systems, and produce a weekly operations summary. Leadership's first idea is "one big autonomous agent with access to everything". The CFO wants to know what the business gets for the spend.

The decisions (answer these before you open the key)

  1. One big agent, or something else?
  2. Structure of the delay investigation
  3. Each worker has a hand-written prompt; a fix to the output rules has to be copied into six places and they keep drifting apart
  4. Workers duplicate each other and return rambling prose
  5. The CFO asks what the platform is worth
  6. Email sorting must meet its SLA at peak; investigations can take longer
  7. Thousands of runs a day, occasional wrong routing, no idea why
  8. A new routing prompt looks better on ten examples
  9. The top model runs every worker and the bill is high
  10. Ops staff fix misrouted emails by hand every day
Answer key (coach key): don't open until you've finished the simulation

1One big agent, or something else?Pick a pattern per need: an augmented LLM call with structured output for email sorting, a fixed workflow for the weekly summary, an agent only for open-ended investigationsOne agent for everything; agents for all three "for consistency"; no AI for the investigationsD1 Select architectural patternsLesson 2, section 1.3
2Structure of the delay investigationOrchestrator-workers: an orchestrator plans and delegates to one worker per system, in parallel, each holding only its own system's tools, then combines the findingsOne agent holding every tool; a fixed chain that always runs every system in order; every worker gets all tools "for flexibility"D1 Multi-agent systems and orchestration; D3 Capability bloatLesson 2, section 1.4; Lesson 1, section 3.1
3Each worker has a hand-written prompt; a fix to the output rules has to be copied into six places and they keep drifting apartOne versioned prompt template: shared blocks (role, output rules, untrusted-content policy) in XML-tagged sections, per-worker variables, and a regression run before any change shipsKeep separate prompts and review them monthly; one giant prompt for all workers; let each worker rewrite its own promptD2 System prompts and templatesLesson 6, section 2.2
4Workers duplicate each other and return rambling proseExplicit task specs: objective, scope boundary, output format and when to stopA longer orchestrator prompt; more workers; a bigger model for the orchestratorD1 Decomposition techniquesLesson 2, section 1.5
5The CFO asks what the platform is worthTie each use case to a value pillar with a baseline measured before launch: handling time (efficiency), cost per case (cost), five-minute routing (performance SLA)A "transformation" story with no numbers; token spend alone; count of agents deployedD1 Align to business value pillarsLesson 2, section 1.6
6Email sorting must meet its SLA at peak; investigations can take longerSet SLAs per path, and choose model and settings per path using eval results on accuracy against latencyThe most capable model everywhere; one SLA for the whole platform; drop accuracy checks to hit latencyD3 Accuracy-latency trade-offsLesson 1, section 3.3
7Thousands of runs a day, occasional wrong routing, no idea whyTracing per run: every step, tool call, token count, latency and error tied to one trace ID, with dashboards, alerts and sampled quality reviewLog only final outputs; read transcripts by hand; wait for complaintsD3 Observability at scale; D4 Monitor with loggingLesson 1, section 3.4; Lesson 3, section 4.6
8A new routing prompt looks better on ten examplesOffline eval first, then an A/B test: split traffic, success metrics set in advance, one change at a time, a rollback planShip to everyone because it looked good; change the prompt and the model together; judge by anecdotesD4 A/B testing and iterative improvementLesson 3, section 4.3
9The top model runs every worker and the bill is highMatch the model to the role: lighter models or lower effort for extraction workers, stronger ones where reasoning matters, confirmed by evalDowngrade everything at once; keep the top model everywhere; cap tokens until answers truncateD2 Model selection; D4 Cost-performance trade-offsLesson 6, section 2.1; Lesson 3, section 4.5
10Ops staff fix misrouted emails by hand every dayClose the feedback loop: capture corrections into the eval set and use them to drive the next prompt iterationIgnore corrections; retrain nothing; ask staff to email the team occasionallyD1 End-to-end architecture with feedback loopsLesson 2, section 1.2

Scoring: 8 or more is a pass. The two principles: use the simplest pattern that meets each need, with agents only for open-ended work, and change one thing at a time and measure it (eval, then A/B) with traces you can read.
