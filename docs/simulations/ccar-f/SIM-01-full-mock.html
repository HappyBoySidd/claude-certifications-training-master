Plain ↔ technical · stop_reason / tool_use

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

In technical terms

stop_reason tool_use tool_result tool_use_id end_turn

Inspect the technical example

Actual Messages content-block shapes; fictional IDs/data; response and next-request excerpts, not a complete API request

Observed assistant response excerpt (stop_reason is RESPONSE metadata):
{"role":"assistant","stop_reason":"tool_use","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}

YOUR runtime executes the permitted lookup. For the next Messages request,
append only assistant role + content, followed by the matching result:
{"role":"assistant","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_order17","content":"{\"order_id\":\"O4\",\"status\":\"delivered\"}"}]}

Send the updated messages array in the next model request.
Do not copy response-only stop_reason into an input message.

Read it as: The tool_use id and tool_result tool_use_id must match. Input messages contain role and content; stop_reason describes the response. The returned content is observed lookup evidence, not a credit receipt.

Official mechanism reference

For a timed mock, use the practice app's mock mode and keep lesson explanations, hints, coach keys and failure-layer replays closed until submission. Existing item identifiers, scoring and progress remain unchanged. The authored scenario layers are learning material, not additional scored mock items.

After submission, classify each miss before opening its lesson: did you misunderstand the application, miss the constraint, confuse similar mechanisms, trust a successful-looking result, or fail to change your answer when a condition changed? Record the governing constraint and the closest rejected alternative, not just the answer letter.

Decision to repairRevisit the plain-language scenarioIndependent retest
Tool selection, approval or ambiguous effectsSupport simulationChange target/amount or timeout state; choose the mechanism again
Repository scope, planning or specific feedbackCode-change simulationContrast a local edit with a cross-file change
Missing specialist context or partial evidenceResearch simulationRemove a mandatory source and identify the blocked conclusion
Capability discovery or stale resumed contextDeveloper simulationSeparate connection, inclusion and authority
Headless output or noisy reviewCI simulationContrast a job error with a valid zero-finding report
Handoff validation or mixed file failuresExtraction simulationDistinguish wrong shape, wrong fact and missing evidence

These diagnostic categories support learning; they are not official scoring categories or a pass guarantee. A retest on the same memorized wording is weaker evidence than explaining the decision under a changed constraint.
