CCDV-F SIM-06 — Customer Chat App: Streaming, Errors and Files

How to use this: read the scene, then work through the decisions on paper, or paste the scene and the decisions list (not the answer key) into Claude and ask it to run the simulation one decision at a time with no hints. Open the coach key only when you've finished.

Primary domains: 2 Applications and Integration (with touches of 5 and 7) · Decisions: 10 · Time: 20 min

Scene (original, written from the official objectives)

You're the developer on a travel-insurance company's claims chat. Customers open it on the website, describe what went wrong, upload photos of damaged luggage and PDF receipts, and can ask Claude to draft a claim letter they then send. The answer has to feel live, the claims system reads a fixed set of fields from each finished chat, and legal says customer data must be processed in the US. Launch is in two weeks, and the first test day went badly.

The decisions (answer these before you open the key)

  1. Testers stare at a blank chat bubble for several seconds before anything appears
  2. The front-end team wants the browser to call the Claude API directly, "to save a hop"
  3. How to send a customer's photo of a torn suitcase
  4. A customer refers back to the same 20-page PDF receipt pack across many turns, and re-sending it each time is slow
  5. The long "draft my claim letter" request fails with an HTTP timeout on the non-streaming call
  6. Halfway through a streamed answer, an overloaded_error event arrives after the HTTP 200
  7. On the test day, every call starts failing with a 429 that has no retry-after header
  8. Each chat gets slower and more expensive the longer it runs
  9. The claims system needs policy number, incident date, item list and amount from each finished chat
  10. Legal: customer data must be processed in the US
Answer key (coach key): don't open until you've finished the simulation

8Each chat gets slower and more expensive the longer it runsThe Messages API is stateless, so every turn resends the history. 9The claims system needs policy number, incident date, item list and amount from each finished chatStructured outputs with a JSON schema: required fields, null allowed when the customer didn't say, then check the meaning in code (the amount matches the receipts)"Please reply in JSON" in the prompt; prefill {; accept anything that parsesD2 Claude Application Design (schema design)Lesson 1, section 2.5, Lesson 4, section 6.5
10Legal: customer data must be processed in the USRead it as an infrastructure requirement and set the data-residency option (inference_geo on the Claude API, or a regional endpoint on a cloud platform). Check which models support it and the price changePut "keep data in the US" in the system prompt; strip names from messages and call it done; ignore it because the servers "are probably in the US"D2 Understanding Requirements (infrastructure requirements)Lesson 1, section 2.1

Scoring: 8 or more is a pass. Decisions 1 and 7 are the heart of the scenario: a person is waiting, so stream it, and read the error before you retry: temporary errors get backoff, a spend cap or a bad request doesn't.
