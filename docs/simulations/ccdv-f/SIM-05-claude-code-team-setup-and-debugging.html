CCDV-F SIM-05 — Claude Code Team Setup, a Cost Check, then Debugging a Failure

How to use this: read the scene, then work through the decisions on paper, or paste the scene and the decisions list (not the answer key) into Claude and ask it to run the simulation one decision at a time with no hints. Open the coach key only when you've finished.

Primary domains: 2 Applications and Integration, 5 Model Selection and Optimization, 3 Claude Code, 4 Eval, Testing, and Debugging · Decisions: 10 · Time: 20 min

Scene (original, written from the official objectives)

Your eight-person team is rolling out Claude Code on a shared monorepo. The lead has been using it alone for months, with most of the setup in personal files. You also own a nightly CI job that runs Claude Code to summarize failing tests as JSON for a team dashboard, plus a small script that calls the Messages API to tag each failing test by area (UI, API or database): a few thousand short calls a night. Setup goes first, then finance asks why the tagging script costs so much. A few weeks later the dashboard starts breaking on some nights and you have to find out why.

The decisions (answer these before you open the key)

  1. A new hire's Claude Code ignores the team's coding conventions. They live in the lead's ~/.claude/CLAUDE.md.
  2. Let Claude run the test command without prompting, but never read .env files
  3. The CI job hangs forever
  4. The tagging script runs on the most capable model and costs more than the rest of CI combined. Tagging is a simple three-way label.
  5. To save money, someone set the tagger's max_tokens very low, and some tags now come back cut off
  6. One night in five the dashboard rejects the JSON. First step?
  7. The trace shows valid JSON from Claude, but the script mixed warning messages into the same stream
  8. Other nights the JSON is valid but sometimes misses the required owner field
  9. The trouble began the day the job's model alias moved to a newer release
  10. You later upgrade the pinned version on purpose, after the evals pass. The next bill shows noticeably more input tokens for the same tests.

Scoring: 8 or more is a pass. The three principles: put shared rules where the whole team gets them (project files, settings), not in personal files or prompt pleas, cut cost with evidence: cheaper settings proven on an eval, and a budget based on measured tokens, and find where the failure starts, integration layer or model output, from the trace before you change anything.
