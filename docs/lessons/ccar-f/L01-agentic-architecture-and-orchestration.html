CCAR-F Lesson 1 — Agentic Architecture and Orchestration (27%, about 16 questions, the BIGGEST)

Learning home and decision coach · Objective map · Application stories
Learn, decide and inspect a worked architecture example here

Understand the domain through its existing application cases, technical decisions and changed constraints.

No installation or API key is required for this reading and decision coach.

Plain ↔ technical: Mechanism examples and terminology · 1.1 · 1.2 · 1.3 · 1.4 · 1.5 · 1.6 · 1.7

Picture the application: A support customer asks about an order and a possible refund. The service should investigate the right account, explain what happened and report only actions actually completed. Agentic architecture is the technical topic: deciding who gathers evidence, how work continues and where executable prerequisites protect the action boundary.

Stage 1 — The assistant asks for a fact, but nobody fetches it

A support worker asks whether order ORD4 can be returned. In the small working version, the application fetches the order and Claude explains it. The broken version stops as soon as Claude asks to call lookup_order: the customer receives no order information. A tool call is a request to the application to do work, not evidence that the work happened.

Original exam-style practice — choose ONE. A Messages API application receives a tool_use block and stop_reason: tool_use. Which implementation correctly advances the agentic loop?

A. Treat the tool request as the final customer answer.

B. Execute the permitted tool, append the assistant turn and matching tool results, then request the next model turn.

C. Discard the assistant turn and send an unrelated user message.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. The application fetches the fact and returns it with the identifier of the request that asked for it. A stops before the work; C loses the connection between request and result. The model proposes a call; application code owns execution and error handling.

Follow the changed path:

customer → Claude tool request → application checks and executes lookup
lookup result + matching call ID → Claude → customer explanation

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Inspect the trace for one request ID, its matching result, and a final answer grounded in that result. A truncated response or exhausted safety cap remains incomplete, even if text exists.

Changed-constraint decision — choose ONE before revealing: The tool reports a timeout. A: return an empty successful order; B: return an explicit failure and let the application apply its bounded recovery policy.

Reveal changed-constraint reasoning

B. No response is different from an order with no return eligibility. Preserve the failed operation and avoid inventing a result.

Stage 2 — Another investigator joins, but receives the wrong brief

The support case now needs both an order check and a policy check. Each specialist works in a separate conversation. The coordinator tells the policy specialist “use what the other agent found,” but sends neither the order nor its evidence. The reply confidently discusses a different product.

Original exam-style practice — choose ONE. Which coordinator-subagent design best preserves context isolation while enabling evidence-grounded synthesis?

A. Assume all subagents inherit the coordinator conversation automatically.

B. Broadcast all transcripts to every specialist indefinitely.

C. Pass a bounded brief containing the task, relevant facts, source references and expected return contract; validate the returned evidence before synthesis.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice C. A separate conversation needs an explicit briefing packet. C supplies what this job requires and lets the receiver check it. A assumes memory that may not exist; B carries unrelated history, extra cost and potentially unnecessary sensitive data.

Follow the changed path:

coordinator → bounded brief → specialist → result + sources + status
receiver checks required fields and evidence → integrated answer

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Remove the order reference from the brief: the specialist must flag missing evidence rather than supply a made-up answer. Restore it and trace the returned claim back to that order.

Changed-constraint decision — choose ONE before revealing: Both checks can be completed reliably with one agent and two tools. A: always add specialists; B: keep the simpler design unless specialization solves a demonstrated requirement.

Reveal changed-constraint reasoning

B. More agents are not a quality guarantee. Split work when independent expertise, context or work boundaries justify the coordination cost.

Stage 3 — A proposal becomes a money movement

The customer now requests a refund. A person approves USD 80 for ORD4, but a later proposal changes to USD 90. The old design remembers only “approved: yes.” That broad flag would let a changed action through.

Original exam-style practice — choose ONE. Which control best enforces approval scope before execution of a side-effecting tool?

A. Instruct Claude to remember the approved amount.

B. Validate the current principal, order, amount and approval validity against the bound proposal in the runtime/backend before submitting the action.

C. Execute first and inspect the model explanation afterward.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. The program compares this exact action with what was approved. A model reminder can help behavior but cannot replace that gate. C finds the problem after money may already move. A hook can intercept an attempted call; business authorization still belongs at the authoritative service boundary.

Follow the changed path:

proposal → approval bound to exact action → runtime/backend gate → business API
changed target, amount or expired approval → deny or request new approval

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Keep the approval record and action fields. Changing one field must block submission; a matching permitted action still needs a real business receipt before being called settled.

Changed-constraint decision — choose ONE before revealing: The write timed out after submission. A: blindly resubmit; B: inspect the business operation status with the operation key before deciding whether retry is safe.

Reveal changed-constraint reasoning

B. Timeout means the caller lacks a result, not that the operation failed. Reconciliation prevents a duplicate effect.

1.0 The big idea

Plain ↔ technical · stop_reason / tool_use

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

In technical terms

stop_reason tool_use tool_result tool_use_id end_turn

Inspect the technical example

Actual Messages content-block shapes; fictional IDs/data; response and next-request excerpts, not a complete API request

Observed assistant response excerpt (stop_reason is RESPONSE metadata):
{"role":"assistant","stop_reason":"tool_use","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}

YOUR runtime executes the permitted lookup. For the next Messages request,
append only assistant role + content, followed by the matching result:
{"role":"assistant","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_order17","content":"{\"order_id\":\"O4\",\"status\":\"delivered\"}"}]}

Send the updated messages array in the next model request.
Do not copy response-only stop_reason into an input message.

Read it as: The tool_use id and tool_result tool_use_id must match. Input messages contain role and content; stop_reason describes the response. The returned content is observed lookup evidence, not a credit receipt.

Official mechanism reference

An agent is a loop: Claude asks for a tool, your code runs it and hands back the result, and this repeats until Claude says it's finished. Bigger jobs split into a coordinator that hands focused pieces to subagents, which see only what you pass them. When a rule must always hold, you enforce it in code, not in the prompt.

1.1 The agentic loop

Related technical reference · stop_reason / tool_use

send request → read stop_reason
  "tool_use"  → run the requested tool(s) → append the results to history → loop
  "end_turn"  → finished
  • Tool results are appended to the conversation history, so Claude can reason about the next step.
  • Handling a tool result, step by step: the assistant turn that asked for the tool stays in history; your code runs every tool_use block in it; then it sends one user turn holding a tool_result for each, matched by tool_use_id. If a tool failed, send the result anyway, marked as an error, so Claude can change course instead of guessing.
  • An iteration cap is a safety net, not the stop signal. Keep a cap so a broken loop can't run up cost forever, but the normal exit is stop_reason: "end_turn". Hitting the cap means something is wrong: log it and fix the design.
  • Model-driven decisions (Claude picks the next tool) vs a pre-set decision tree. Know the difference. Model-driven means Claude reads each tool result and chooses the next step itself. A pre-set decision tree means your code fixes the order of steps in advance, whatever the results say. The exam cares because questions about loops and tools test whether you let Claude decide when the path depends on what it finds.
  • Anti-patterns (these are the wrong answers):
    • parsing natural language ("I'm done") to decide when to stop
    • an arbitrary iteration cap as the main stop signal
    • treating "the assistant returned text" as the completion signal

1.2 Coordinator and subagents (hub and spoke)

Related technical reference · stop_reason / tool_use

  • The coordinator handles all communication between subagents, error handling and routing. It decomposes the task, delegates it and aggregates the results.
  • Subagents have isolated context. They don't inherit the coordinator's history.
  • Route all subagent traffic through the coordinator, for observability and consistent error handling.
  • Pick subagents dynamically according to how complex the query is. Don't always run the full pipeline.
  • Partition the scope (distinct subtopics or source types) to avoid duplicated work.
  • Risk: decomposition that's too narrow leaves gaps in coverage. The fix is an iterative refinement loop: the coordinator checks the synthesis for gaps, re-delegates targeted queries, and re-synthesizes.

1.3 Spawning subagents and passing context

Related technical reference · stop_reason / tool_use

  • Saved-guide terminology: task 1.3 uses the Task tool and its permission configuration for delegation. Current Claude Code uses Agent (Task remains an alias), and allowedTools pre-approves permission prompts; do not treat it as a complete tool-availability or downstream authorization policy. Compare saved-guide wording with current contracts.
  • Context must be passed explicitly in the prompt, because there's no shared memory. Pass complete findings, for example the search results and the analysis output going to synthesis.
  • Use structured formats to separate content from metadata (URL, document, page) so attribution survives.
  • Parallel spawning means several Task calls in one coordinator response, not spread across turns.
  • Give coordinator prompts goals and quality criteria, not step-by-step procedures, so subagents can adapt.
  • AgentDefinition (the Agent SDK object that describes one kind of subagent) holds the description, system prompt and tool restrictions for each subagent type.
  • Design the handoff: isolated workers return a report rather than automatically sharing their whole context. Require findings, exact source locators, relevant failure excerpts and artifact paths. Current Claude Code can persist/resume worker transcripts; this does not automatically put their evidence into the parent's context.
  • Choose delegation for a reason: keep small or tightly coupled work together when handoffs lose evidence or add latency. Sequential workers and test runners can help when their reports preserve what the next step needs. Scope tools to authorized work; a role label alone does not establish expertise or correctness. (subagent guidance, checked 2026-10-21.)

1.4 Enforcement and handoff

Related technical reference · stop_reason / tool_use

  • Programmatic enforcement (hooks, prerequisite gates) vs prompt guidance. When compliance must be deterministic, prompts alone fail some of the time.
  • Classic example: block process_refund until get_customer has returned a verified customer ID.
  • For a request with several concerns, split it into items, investigate them in parallel with shared context, then give one resolution.
  • Handoff to a human: a structured summary with the customer ID, root cause, amount and recommended action. The human can't see the transcript.

1.5 Agent SDK hooks

Related technical reference · stop_reason / tool_use

A hook is your own code that the Agent SDK runs at a fixed point in the loop. Each row is one hook point; the "Use" column says what you would do there.

HookUse
PostToolUseTransform results before the model sees them. For example, normalize Unix, ISO 8601 and numeric status codes coming from different MCP tools.
PreToolUse (tool-call interception)Block actions that break policy, such as a refund over $500, and redirect to human escalation

PreToolUse runs before the tool and sees only the inputs; PostToolUse runs after and sees the result.

Current hook contracts (implementation context for objective 1.5). An Agent SDK PreToolUse callback can return hookSpecificOutput containing hookEventName: "PreToolUse", permissionDecision: "deny" and a reason. {} makes no overriding decision; other permissions still apply. PostToolUse can transform observed output but cannot prevent a completed effect. Current SDK pre-tool callback timeout blocks the call; check the installed runtime contract.

Claude Code command hooks use a separate contract:

ResultInterpretation
Exit 0Parse supported stdout JSON; its decision may deny, ask, allow or leave normal checking in place.
Exit 2Blocks on a blockable event and reports the reason.
Other exit or timeoutNormally no blocking hook decision; normal permission checks still apply.

Current command/HTTP hooks support onFailure: "block" from version 2.1.295. A post-tool failure cannot undo execution. Enforce mandatory predicates at a supported pre-effect hook or action service, with complete effect-path coverage and tested rejection/failure handling. Instructions explain desired behavior; they do not implement enforcement.

Current fail-closed command-hook illustration (requires a real, tested script and supported version):

{ "hooks": { "PreToolUse": [ { "matcher": "Edit|Write",
  "hooks": [ { "type": "command", "onFailure": "block",
    "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/check-path.sh" } ] } ] } }

Sources: SDK hooks, command hooks, checked 2026-10-21. A matcher covers only matched tool paths; this example does not establish complete application security.

Prompts guide; executable checks enforce stated predicates. Choose a supported pre-effect hook or service guard for a mandatory rule. Correctness depends on event timing, trustworthy inputs, tested rejection behavior and coverage of every effect path. A post-tool transform cannot prevent an already completed action; deterministic code alone does not prove business truth.

1.6 Breaking the task down

Related technical reference · stop_reason / tool_use

PatternUse for
Prompt chaining, a fixed sequencePredictable reviews with several parts. For example, analyze each file, then run a cross-file integration pass.
Dynamic, adaptive decompositionOpen-ended investigation. For example, "add tests to a legacy codebase": map the structure, find high-impact areas, plan by priority, and adapt as you go.

Splitting a large review per file avoids attention dilution (when one prompt holds too much, the model spreads its focus thin and misses details).

How to choose: if you can write the steps down before you start and they won't change, chain them; each step's output feeds the next, and each is easy to test on its own. If the next step depends on what the last one found, let the agent decompose as it goes. A common exam shape mixes them: a fixed chain whose middle step is an open-ended investigation handed to a subagent.

1.7 Sessions: resume and fork

Related technical reference · stop_reason / tool_use

  • --resume <session-name> continues a named session. (--resume and --continue are flags on Claude Code's command line; Lesson 3: Claude Code Configuration and Workflows covers it.)
  • fork_session creates independent branches from a shared starting point, for example to compare two refactoring approaches. It means: copy the session so far into a new session, and leave the original untouched. On the CLI that's --fork-session together with --resume or --continue; in the Agent SDK it's the fork_session option (forkSession in TypeScript; check the current docs).
  • If the earlier context is mostly valid, resume, and tell the agent which files changed for targeted re-analysis. If the tool results are stale, start fresh with an injected structured summary, which is more reliable.
  • Fork or resume? Resume when you want to carry on down one path. Fork when you want to try two or more paths from the same point without one polluting the other, then keep the winner. Neither helps if the shared starting context is itself stale; then start fresh with a summary.

Worked example (official sample)

Related technical reference · stop_reason / tool_use

In 12% of cases the agent skips get_customer and calls lookup_order with only a name, which leads to wrong refunds. Answer: a programmatic prerequisite that blocks lookup_order and process_refund until there's a verified ID. More system-prompt wording, more few-shot examples or a routing classifier are all probabilistic fixes for a rule that has to be deterministic.
