D01 — Authorize the exact action

Plain ↔ technical · execution-time authorization / prerequisite gate

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

The program that can change a record must check the prerequisites immediately before the change. If blocked, pass the next owner a complete case.

Does not establish: Selecting the right tool or passing JSON validation does not authorize that action.

In technical terms

execution-time authorization prerequisite gate scoped approval human handoff

Inspect the technical example

Application control-flow pseudocode — fictional policy, not a Claude API feature

if trusted_session.account != order.owner:
    return blocked("ownership_mismatch")
if proposed_cents > 18000 and not scoped_staff_approval:
    return pending_review(case, evidence, proposed_cents, operation_state)
submit_credit(permitted_exact_action)

Read it as: The trusted login comes from the application, not the proposed tool arguments. The review packet says whether money was submitted or is only proposed.

Equivalent decision procedure: Identify target and effect. Verify identity binding. Check current scoped approval. Block failed checks. Execute only the authorized effect. Record a receipt; unknown outcome requires status reconciliation before retry.

Assumptions and exception: The fictional application defines which reads and effects require approval; a prompt does not enforce this boundary.

D02 — Choose the agent structure

Plain ↔ technical · coordinator-subagent pattern / bounded delegation

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Specialists investigate bounded parts of a question. One coordinator still checks whether the whole question was answered.

Does not establish: More workers do not establish complete coverage, and agreement among workers does not establish source authority.

In technical terms

coordinator-subagent pattern bounded delegation coverage ledger synthesis

Inspect the technical example

Application orchestration pseudocode — not Agent SDK fields

required = ["connectivity", "glove_use", "training"]
delegate("connectivity", scoped_brief)
delegate("glove_use", scoped_brief)
coordinator_owns("training")
reconcile(required, observed_returns)
synthesize(source_linked_claims, explicit_gaps)

Read it as: The coordinator retains training and integration instead of assuming every concern belongs to a worker. A missing return remains a gap.

Equivalent decision procedure: Define required evidence dimensions. Prefer a sufficient scoped single agent. Use a deterministic workflow for known dependencies; use bounded specialists for independent investigations. The coordinator checks coverage and conflicts, then dispatches targeted gaps.

Assumptions and exception: Tool count alone is not the deciding criterion; costs and real evidence boundaries matter.

D03 — Pass evidence and propagate partial results

Plain ↔ technical · isolated context / self-contained brief

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

An isolated specialist needs the actual assignment and relevant facts, not a reference to a conversation it has not received.

Does not establish: An output schema does not supply missing task context; these field names are not reserved Claude API fields.

In technical terms

isolated context self-contained brief return contract claim-to-source mapping

Inspect the technical example

Illustrative application brief/return contract — not SDK invocation syntax

brief = {
  goal: "Compare scanner use with gloves",
  constraint: "Pilot next month",
  sources: ["S1", "S2"],
  return: ["claim", "source_id", "locator", "uncertainty"]
}
return = {claim:"...", source_id:"S1", locator:"p4", uncertainty:"..."}

Read it as: The fields are your application agreement. They tell the specialist what to investigate and let the coordinator trace each finding.

Equivalent decision procedure: Send an explicit brief to the isolated specialist. Require source-tagged findings and structured failures. Check mandatory dimensions. Preserve successes while recovering gaps or stopping dependent claims.

D04 — Recover according to the result

Plain ↔ technical · tool_result / is_error

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Return a clear observed failure so the next decision can distinguish bad input, temporary trouble and an unknown financial effect.

Does not establish: An execution error result is not a successful empty response. Transport failure does not establish that a financial write failed.

In technical terms

tool_result is_error tool_use_id protocol error

Inspect the technical example

Actual Messages tool_result shape; content JSON is a fictional application error contract

{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_credit17","is_error":true,"content":"{\"code\":\"provider_timeout\",\"operation_id\":\"r17\",\"effect\":\"unknown\"}"}]}

Read it as: is_error belongs to a Messages result block. code, operation_id and effect are authored application data inside content, not reserved Messages fields. Do not confuse this result block with a different protocol’s error envelope.

Official mechanism reference

Purpose: Choose the mechanism and identify its recovery boundary. Legend: numbered nodes mark order; diamonds ask a condition; labelled arrows show the selected branch. Sequence lanes name separate owners.

flowchart TD
 A[1 Tool response] --> B{2 Outcome category}
 B -->|Success with empty records| C[3 Clarify filters or report none]
 B -->|Malformed input| D[4 Repair arguments]
 B -->|Transient read failure| E[5 Bounded retry]

Equivalent decision procedure: Separate protocol outcome from application payload. Empty successful records mean no match. Repair invalid arguments. Retry only eligible transient operations within a budget. Authorization needs changed permission. Uncertain writes need status lookup.

Assumptions and exception: A retryable transport failure does not prove a repeated write is safe.

D05 — Preserve lineage across systems

Plain ↔ technical · MCP / JSON-RPC

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

An MCP connection advertises capabilities. Your client still has to discover the tool, call it and bring back the result. A project-wide connection is different from one person’s local setup.

Does not establish: Configured server, discovered tool and completed tool execution are three different states. MCP metadata does not grant business authorization.

In technical terms

MCP JSON-RPC tools/list tools/call inputSchema .mcp.json project scope resources/read

Inspect the technical example

Actual MCP tools/call request shape; fictional tool/data, not a Messages tool_use block

{"jsonrpc":"2.0","id":17,"method":"tools/call","params":{"name":"lookup_order","arguments":{"order_id":"O4"}}}

Before this call: discover the available tool and its inputSchema through tools/list.
After it: inspect the actual MCP result/error before adapting it into your model conversation.

Resource content is a different protocol operation:
{"jsonrpc":"2.0","id":3,"method":"resources/read","params":{"uri":"manual://M4/R3"}}
Response excerpt:
{"jsonrpc":"2.0","id":3,"result":{"contents":[{"uri":"manual://M4/R3","mimeType":"text/plain","text":"Approved M4-R3 procedure..."}]}}

Read it as: MCP method and params belong to the client-server protocol. Anthropic Messages uses tool_use/input and tool_result instead; an adapter connects the two boundaries. tools/call invokes a capability; resources/read reads content at a URI. A catalog entry naming the URI is not its text and does not prove the model received it.

Assumptions and exception: Federation must actually be supported by the chosen host/interface; it does not establish source accuracy.

D06 — Select the runtime by dependency

Plain ↔ technical · Message Batches / custom_id

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A completed batch can contain different outcomes, and its result order need not match submission order. Keep identity and business acceptance separate.

Does not establish: Batch ended is not all-item success. API succeeded is not source-correct extraction, and a proposed tool call is not a local executor.

In technical terms

Message Batches custom_id processing_status succeeded errored canceled expired JSONL

Inspect the technical example

Actual batch result identity/outcome fields; message body omitted from this response excerpt

{"custom_id":"N-3-v1","result":{"type":"succeeded","message":{"role":"assistant","content":[{"type":"text","text":"..."}],"stop_reason":"end_turn"}}}

Illustrative consumer ledger:
N-3-v1 -> API succeeded -> business validation pending
N-1-v1 -> API errored -> inspect error cause
N-2-v1 -> API succeeded -> downstream accepted

Read it as: custom_id joins each response to its source/version. result.type is the per-request API outcome; processing_status is the batch-level state. The ledger’s validation states are application-defined.

D07 — Understand side-effect timing

Plain ↔ technical · PreToolUse / PostToolUse

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A before-action hook can stop a prohibited call. An after-action hook can inspect an observed result, but cannot undo a completed side effect.

Does not establish: A PostToolUse check cannot retroactively prevent an effect that has already occurred; hook control is not a replacement for business authorization.

In technical terms

PreToolUse PostToolUse hookSpecificOutput permissionDecision

Inspect the technical example

Actual PreToolUse hook JSON decision shape; illustrative denial reason

{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"This action is outside the permitted task scope."}}

Read it as: This is hook output for the named lifecycle event, not a message sent as tool_result. Hook behavior depends on the event; verify the configured handler actually runs.

D08 — Validate a CI report before gating

Plain ↔ technical · claude -p / --output-format json

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A CI job must finish or fail visibly without waiting for a person at a terminal. Keep review authority separate from posting, approval and merge authority.

Does not establish: A valid empty findings list is not proof of safe code, and a reviewer has no implicit authority to publish comments or merge.

In technical terms

claude -p --output-format json headless execution exit status result envelope bounded permissions

Inspect the technical example

Actual CLI flags with a fictional supplied review packet; illustrative shell invocation, not a complete CI deployment

claude -p "Review the supplied change against its contract" --output-format json < review-packet.txt > review-result.json

Consumer checks, in order:
1. Process completed successfully.
2. Expected result envelope is present and reports an acceptable run outcome.
3. Review payload parses and passes its contract.
4. Findings have independently checked code evidence.

Read it as: The command runs noninteractively and requests JSON output. The application must still check process and envelope status before interpreting a payload. Configure bounded permissions and credentials separately.

Official mechanism reference

 A[1 CLI process and exit status] --> B[2 Parse documented envelope]
 B --> C[3 Extract expected findings payload]

Only then apply a reviewed gate policy. Missing credentials, parse errors or empty unexpected payloads remain visible failures.

D09 — Keep invocation, shape and truth separate

Plain ↔ technical · output_config.format / json_schema

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Choose the mechanism for the boundary you need: a machine-readable final response or valid arguments for a requested tool. Then check whether the values are actually supported.

Does not establish: Valid JSON and schema-compliant integers do not establish correct units, source truth, permissions or completed business effects.

In technical terms

output_config.format json_schema strict:true input_schema schema conformance

Inspect the technical example

Actual request-field fragment for final structured JSON; model and remaining request fields omitted

{"output_config":{"format":{"type":"json_schema","schema":{"type":"object","properties":{"total_minor":{"type":"integer"},"currency":{"type":"string","enum":["USD"]}},"required":["total_minor","currency"],"additionalProperties":false}}}}

For supported strict tool arguments, strict:true belongs on the tool definition;
it is not the same field as output_config.format.

Read it as: This fragment constrains final JSON shape. Strict tool use constrains a different boundary. Verify current model/schema support and handle refusals or incomplete responses before consuming results.

D10 — Handle missing values and wrong values differently

Plain ↔ technical · stop_reason / tool_use

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

In technical terms

stop_reason tool_use tool_result tool_use_id end_turn

Inspect the technical example

Actual Messages content-block shapes; fictional IDs/data; response and next-request excerpts, not a complete API request

Observed assistant response excerpt (stop_reason is RESPONSE metadata):
{"role":"assistant","stop_reason":"tool_use","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}

YOUR runtime executes the permitted lookup. For the next Messages request,
append only assistant role + content, followed by the matching result:
{"role":"assistant","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_order17","content":"{\"order_id\":\"O4\",\"status\":\"delivered\"}"}]}

Send the updated messages array in the next model request.
Do not copy response-only stop_reason into an input message.

Read it as: The tool_use id and tool_result tool_use_id must match. Input messages contain role and content; stop_reason describes the response. The returned content is observed lookup evidence, not a credit receipt.

For instruction decisions, inspect path scope, actual loading and conflicts. For skill decisions, establish repeated need, discovery and inputs, then preserve downstream authorization. These companion lanes add no new automatic runtime guarantee.

D12 — Evaluate important slices and resolve review disagreements
