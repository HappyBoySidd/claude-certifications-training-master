CCAR-F Lesson 2 — Tool Design and MCP Integration (18%, about 11 questions)

Learning home and decision coach · Objective map · Application stories
Learn, decide and inspect a worked architecture example here

Understand the domain through its existing application cases, technical decisions and changed constraints.

No installation or API key is required for this reading and decision coach.

Plain ↔ technical: Mechanism examples and terminology · 2.1 · 2.2 · 2.3 · 2.4 · 2.5

Picture the application: A researcher submits a PDF, but the assistant repeatedly sends it to an operation meant for another kind of content. The expected result is analysis from the appropriate source with an understandable outcome. Tool design and MCP integration name the technical choices that make capabilities discoverable, distinguishable and usable.

Learn this domain through connected case studies

Read and predict; no account, code execution or setup is required for these teaching scenes. Each stage names its application and the requirement that fails. Some stages transfer the same decision to a different application; follow the named people and data rather than assuming every stage belongs to one system. The original reference sections remain below for detail. These are original teaching questions, not claimed live exam items. Write your choice before revealing the repair. Diagrams below show AI reasoning and ordinary software checks explicitly in their labels.

Stage 1 — Two tools sound equally useful

A service assistant handles a balance question and an address change. Both tools are named manage_account and described as “manage customer data.” A balance request sometimes triggers the write operation. The working one-tool demo hid this ambiguity.

Original exam-style practice — choose ONE. Which tool-interface change most directly improves selection reliability while preserving the read/write boundary?

A. Use one generic tool and explain all differences in a long system prompt.

B. Give each capability a distinct purpose, precise description, input schema and side-effect boundary.

C. Add more overlapping aliases so the model has more options.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. Name the actual job, such as read balance versus propose address change, and state when each is appropriate. A hides the distinction inside one broad interface; C increases confusion. A schema describes accepted arguments; authorization is a separate check.

Follow the changed path:

customer need → distinct tool purpose → typed arguments → runtime authorization → service result

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Use a balance request and an address request. Record the selected capability and arguments separately from permission and execution outcome. A selected write tool does not authorize the write.

Changed-constraint decision — choose ONE before revealing: The model chooses the correct tool but supplies an invalid account ID. A: redesign names alone; B: validate arguments and return a specific correctable error without executing.

Reveal changed-constraint reasoning

B. Correct selection and valid arguments are different requirements. Repair the failing layer.

Objective connections: 2.1, 2.3.

Stage 2 — An unavailable service looks like an empty account

The balance tool normally returns current funds. Today the server cannot reach the bank service. It returns an empty list and the assistant says the customer has no accounts. The error was hidden as ordinary data.

Original exam-style practice — choose ONE. Which MCP tool-result contract best supports correct error propagation and recovery?

A. Return an empty successful result on every failure.

B. Return an explicit failure category and useful retryability context without exposing secrets; preserve available partial data as partial.

C. Ask the model to infer the failure from response length.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. The caller must distinguish “there are no accounts” from “we could not check.” A confuses those meanings; C guesses. Permission denial, invalid input, insufficient stock and transient outage need different responses.

Follow the changed path:

business API failure → tool failure category → caller recovery policy
confirmed empty data → successful empty result → ordinary answer

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Inject a timeout, bad input and permission denial. Expect different categories; do not retry permanent invalid input as though waiting would fix it.

Changed-constraint decision — choose ONE before revealing: The service denies access. A: retry with higher model confidence; B: stop that action and use the approved permission/escalation route.

Reveal changed-constraint reasoning

B. Confidence cannot grant access. Keep access failures separate from temporary outages.

Objective connections: 2.2.

Stage 3 — The server is configured, but the capability is absent

A developer connects a document-search MCP server. The connection appears healthy, yet the agent cannot search documents. The tool was not included in that agent’s available capability set.

Original exam-style practice — choose ONE. Which diagnosis correctly distinguishes MCP connectivity, tool availability and authorization?

A. Treat a successful server connection as proof every agent may execute every server tool.

B. Verify server discovery/health, the agent’s exposed tool set, and the service authorization independently.

C. Add credentials to the user-facing prompt so the model can repair access.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. A working connection is a doorway, not proof that this agent has the search tool or permission to use it. A merges three checks; C exposes secrets and does not create a legitimate control.

Follow the changed path:

configured server → discovered tool → included in agent scope → authorized request → result

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Compare discovery output with the agent-visible tool list and an authorized synthetic test. Redact credentials from retained logs.

Changed-constraint decision — choose ONE before revealing: No external service is needed; a repository filename pattern is known. A: use local Glob then Read; B: introduce MCP solely because it is available.

Reveal changed-constraint reasoning

A. Choose the local capability that matches the job. Search content with Grep; locate matching paths with Glob; inspect selected files with Read.

2.0 The big idea

Plain ↔ technical · tools / name

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Give each capability a clear job, inputs and effect so the model can distinguish reading an order from changing its financial record.

Does not establish: A descriptive side-effect warning helps selection but is not an execution permission check.

In technical terms

tools name description input_schema required side effect

Inspect the technical example

Actual user-defined tool-definition shape; fictional read-only capability

{"name":"lookup_order","description":"Read delivery status for one order accessible to the current caller. Does not issue credits or change orders.","input_schema":{"type":"object","properties":{"order_id":{"type":"string","description":"Order identifier from the current case."}},"required":["order_id"],"additionalProperties":false}}

Read it as: name identifies the capability; description explains when to use it; input_schema constrains the arguments. Your runtime still enforces access.

Official mechanism reference

Claude picks a tool by reading its name and description, so clear, non-overlapping descriptions matter more than anything you add to the prompt. Give each agent a few tools that fit its job, and make failures say what went wrong and whether a retry could help. MCP is how you plug those tools into Claude Code and agents, with the right scope for who should share them.

2.1 Tool descriptions are how the model chooses

Related technical reference · tools / name

  • A description is the main thing the model uses to pick a tool. Thin descriptions mean unreliable choices between similar tools.
  • Include input formats, example queries, edge cases and boundaries: when to use this tool and when to use its neighbor instead.
  • Overlapping tools (analyze_content vs analyze_document) get misrouted. Rename them and sharpen the descriptions, for example extract_web_results with a web-specific description.
  • Split a generic tool into purpose-specific ones: extract_data_points, summarize_content, verify_claim_against_source.
  • Check the system prompt for keyword-sensitive wording that overrides good descriptions.

2.2 Structured errors

Related technical reference · tools / name

  • The MCP isError flag tells the agent a tool call failed.
  • On the Messages API the tool_result field is is_error; in MCP it is isError. Same idea, two layers.
  • Error types: transient (timeout, service unavailable), validation (bad input), business (policy), permission.
  • Return errorCategory, isRetryable and a readable description. For business-rule violations, set retriable: false and include a customer-friendly explanation.
  • Only isError is an MCP field. errorCategory and isRetryable/retriable are fields you design into your own error payload; the guide spells the retry flag both ways, so don't read anything into the spelling.
  • A uniform "Operation failed" stops the agent recovering well.
  • An access failure is not a valid empty result. A timeout needs a retry decision. "No matches" is a successful query.
  • Subagents recover locally from transient errors and pass up to the coordinator only what they can't fix, along with partial results and what they tried.

2.3 How many tools, and which ones

Related technical reference · tools / name

  • Smallest sufficient role-relevant tool set. The saved guide contrasts 4–5 relevant tools with 18 indiscriminate tools; that is an example, not a quota. Scope by the work, relevant cross-role needs and discovery costs.
  • Irrelevant capabilities increase the risk of mistaken tool selection; legitimate narrow cross-role needs can still be appropriate. For example, a synthesis worker should not start unrelated broad web searches merely because a search tool is available.
  • Give scoped access, plus narrow cross-role tools for frequent needs (for example verify_fact for synthesis). Route complex cases through the coordinator.
  • Replace generic tools with constrained ones: fetch_url becomes load_document, which checks URLs.
  • tool_choice: the request setting that says whether Claude may answer in text or must call a tool. Each row is one value; read across for what Claude does and when to pick it.
ValueBehaviorUse
"auto"Model may reply in textNormal chat
"any"Must call some toolGuarantee structured output when the document type is unknown
{"type":"tool","name":"X"}Must call XForce extract_metadata to run first, then handle the rest in later turns

These are the three options the exam tests (exam guide, task 2.3). Today the API also has a fourth, {"type": "none"}, which turns tools off; see exam answer vs today.

2.4 MCP servers in Claude Code and agents

Related technical reference · tools / name

An MCP server's scope is who gets it: the whole team or only you. Each row is one scope; read across for the file it lives in and who it is for.

ScopeFileFor
Project.mcp.json (committed)Shared team tooling. Use ${GITHUB_TOKEN} expansion so secrets aren't committed.
User~/.claude.jsonPersonal or experimental servers
Local (the default)~/.claude.json, under the project's pathJust you, in just this project. It loads only in that project.
  • Tools from all configured servers are discovered when the connection starts and are all available at once. Exam wording (task 2.4): "That tools from all configured MCP servers are discovered at connection time and available simultaneously to the agent". Today Claude Code's tool search is on by default: only tool names and server instructions load at the start, and full definitions load when Claude needs them; see exam answer vs today. On supported current models/platforms, the default is tool search. To turn it off, set ENABLE_TOOL_SEARCH=false (every tool loads upfront). On Google Cloud's Agent Platform, models older than the 4.5 generation also load every tool upfront. The "10% of the context window" figure you may see in course videos belongs to the opt-in auto threshold mode, not the default (MCP docs, checked 2026-10-21, Tier 1).
  • Transport and discovery: common connections use local stdio or remote HTTP; host support can differ. Protocol tool discovery and calls use tools/list and tools/call; SDK helper names can differ. (MCP tools.)
  • The three server primitives differ by who controls them (MCP server primitives, checked 2026-10-21):
PrimitiveControlled byExample use
ToolThe model (Claude decides when to call it)Create a ticket in the tracker
ResourceThe app (your code decides when to fetch it)Inject a document's text when the user @-mentions it
PromptThe user (a click, menu pick or slash command)A ready-made "review this PR" workflow
  • MCP resources expose content catalogs (issue summaries, doc trees, database schemas) so the agent doesn't need exploratory calls. A direct resource has a fixed URI; a templated one has parameters in the URI, such as a document ID (resource contracts).
  • Choose the boundary: tools expose capabilities, skills package reusable instructions/work, and MCP standardizes access to tools and context from your own or external services. Primitive control categories are interaction patterns, not permission grants. Apply authorization and least privilege separately. (MCP primitives.)
  • If the agent prefers Grep over a more capable MCP tool, improve the MCP tool's description.
  • Use a community server for standard integrations such as Jira. Build custom servers only for team-specific workflows.

Server tools vs client tools (who runs the loop)

Related technical reference · tools / name

KindExecution and continuation responsibility
Server toolAnthropic executes the handler; your application still checks results, errors and stop reasons.
Client toolYour application or chosen host/SDK executes the handler and supplies correlated tool_result messages.

A raw Messages API client implements dispatch/continuation; a suitable runner may manage it. Server tools can return pause_turn, requiring continuation, and mixed server/client calls can wait for client results. Tool selection alone does not prove execution or business completion. Check support for the selected model, platform and feature combination.

Sources: tool overview, server tools, checked 2026-10-21.

2.5 Built-in tools

Related technical reference · tools / name

ToolFor
GrepSearching content: function callers, error messages, imports
GlobMatching file paths, such as **/*.test.tsx
Read / WriteWhole-file operations
EditA targeted change anchored on unique text. If the text isn't unique, fall back to Read, then Write.
BashCommands

Build understanding step by step: Grep for entry points, then Read to follow imports. Don't read everything up front. For wrapper modules, list the exported names first, then Grep for each one.

Worked example

Related technical reference · tools / name

The research agent keeps calling analyze_content for PDFs, which are meant for analyze_document. Answer: rename and re-describe the tools so they don't overlap, adding input formats and when to use each. Adding "prefer analyze_document for PDFs" to the prompt, or a routing classifier, doesn't fix the root cause.

Traps

Related technical reference · tools / name

  • "Give every agent every tool, just in case."
  • "Return an empty list when the search times out." That's silent error suppression.
  • "Put the API token directly in .mcp.json." Use ${ENV} expansion.
  • Mixing up Grep (content) and Glob (paths).
  • Watch out: some videos say "Bash is always wrong." The guide doesn't say that. The guide picks Grep, Glob, Read and Edit for file work; Bash is for running commands (exam guide task 2.5, Tier 1).
  • Watch out: some videos get three details wrong. The user file is ~/.claude.json, not "cloud.json". The guide gives only "18 instead of 4-5"; bands such as "6–10 is acceptable" aren't in it. And the guide spells the flags isRetryable and retriable, never snake_case "is_retriable" (exam guide tasks 2.2–2.4, Tier 1).
