Objective 1.1 · stop_reason / tool_use

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

In technical terms

stop_reason tool_use tool_result tool_use_id end_turn

Actual Messages content-block shapes; fictional IDs/data; response and next-request excerpts, not a complete API request

Observed assistant response excerpt (stop_reason is RESPONSE metadata):
{"role":"assistant","stop_reason":"tool_use","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}

YOUR runtime executes the permitted lookup. For the next Messages request,
append only assistant role + content, followed by the matching result:
{"role":"assistant","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_order17","content":"{\"order_id\":\"O4\",\"status\":\"delivered\"}"}]}

Send the updated messages array in the next model request.
Do not copy response-only stop_reason into an input message.

Read it as: The tool_use id and tool_result tool_use_id must match. Input messages contain role and content; stop_reason describes the response. The returned content is observed lookup evidence, not a credit receipt.

In everyday language

Specialists investigate bounded parts of a question. One coordinator still checks whether the whole question was answered.

Objective 1.6 · prompt chaining / routing

In everyday language

Choose the simplest work pattern that fits what you know. A fixed recipe suits known steps; an evolving investigation may need a coordinator to choose the next question.

Does not establish: A fixed workflow is not automatically an autonomous agent; adding agents does not fix a missing deterministic check.

In technical terms

prompt chaining routing parallelization orchestrator-workers evaluator-optimizer

Inspect the technical example

Architecture selection pseudocode — not an API configuration

if steps_known_and_dependent: use_fixed_chain()

Read it as: These are alternative designs, not mandatory layers to add together. Independent tasks can run together; a step needing another result must wait.

Objective 1.7 · session_id / resume

In everyday language

A saved conversation helps you continue an investigation. It does not refresh an old policy or give permission for a different payment.

Does not establish: Persisted session history is not a filesystem snapshot, current authorization or proof that an unknown transaction failed.

In technical terms

session_id resume fork conversation history freshness check

Inspect the technical example

Application resume policy pseudocode — not an Agent SDK call signature

Read it as: Session restoration and business-state revalidation are different jobs. Forking branches a conversation; it does not roll back external payments or files.

Objective 2.3 · tools allowlist / tool_choice

In everyday language

Limit which capabilities a task can request, then decide whether the model may choose freely or must request a specific tool. Neither setting grants business permission.

Does not establish: tool_choice is not an authorization mechanism; strict arguments do not select the right capability or prove the result.

In technical terms

tools allowlist tool_choice auto any tool none

Inspect the technical example

Actual request-field fragments — alternative configurations, not one combined request

Available capability set for a read-only task:
"tools": [lookup_order_definition]

Let the model decide whether a tool is needed:
"tool_choice": {"type":"auto"}

When this specific lookup is required:
"tool_choice": {"type":"tool","name":"lookup_order"}

Other documented modes: {"type":"any"} or {"type":"none"}

Read it as: The tools list controls what is available; tool_choice controls selection behavior. any requires a tool but does not name which one. Forced modes require compatible models/settings; verify support before selecting them.

Objective 2.4 · MCP / JSON-RPC

In everyday language

An MCP connection advertises capabilities. Your client still has to discover the tool, call it and bring back the result. A project-wide connection is different from one person’s local setup.

Does not establish: Configured server, discovered tool and completed tool execution are three different states. MCP metadata does not grant business authorization.

In technical terms

MCP JSON-RPC tools/list tools/call inputSchema .mcp.json project scope resources/read

Inspect the technical example

Actual MCP tools/call request shape; fictional tool/data, not a Messages tool_use block

{"jsonrpc":"2.0","id":17,"method":"tools/call","params":{"name":"lookup_order","arguments":{"order_id":"O4"}}}

Before this call: discover the available tool and its inputSchema through tools/list.
After it: inspect the actual MCP result/error before adapting it into your model conversation.

Resource content is a different protocol operation:
{"jsonrpc":"2.0","id":3,"method":"resources/read","params":{"uri":"manual://M4/R3"}}
Response excerpt:
{"jsonrpc":"2.0","id":3,"result":{"contents":[{"uri":"manual://M4/R3","mimeType":"text/plain","text":"Approved M4-R3 procedure..."}]}}

Read it as: MCP method and params belong to the client-server protocol. Anthropic Messages uses tool_use/input and tool_result instead; an adapter connects the two boundaries. tools/call invokes a capability; resources/read reads content at a URI. A catalog entry naming the URI is not its text and does not prove the model received it.

Objective 2.5 · Glob / Grep

In everyday language

First find the relevant files, then inspect their contents, and only then make a small change. Tool names describe different jobs, not interchangeable ways to guess what a repository contains.

Does not establish: A search hit is not the whole implementation, and a successful edit is not a successful test or deployed change.

In technical terms

Glob Grep Read Edit Write Bash targeted exploration

Inspect the technical example

Claude Code tool workflow pseudocode — semantic jobs, not tool-call JSON signatures

Glob: locate **/importer.py and related test paths
Grep: find deposit uses and report-formatting callers
Read: inspect current importer, formatter and relevant fixtures
Edit: change the specific proven boundary
Bash: run the relevant check and capture its actual outcome

Read it as: Glob locates paths; Grep locates matching content; Read supplies current code evidence. An Edit changes a known region; Write can replace file content and therefore needs a justified scope.

Objective 3.2 · SKILL.md / YAML frontmatter

In everyday language

A skill packages a repeatable procedure. You can expose it as a named command and decide whether Claude may invoke it automatically.

Does not establish: A skill’s allowed-tools list is not a tool allowlist that excludes everything else. Skill instructions and preapproval do not replace runtime permission enforcement or prove evidence-based execution.

In technical terms

Objective 3.5 · reproduction / expected versus observed

In everyday language

Give the next iteration the exact failing example and expected result. “Try harder” does not tell the coding agent what survived the first patch.

Objective 3.6 · claude -p / --output-format json

In everyday language

A CI job must finish or fail visibly without waiting for a person at a terminal. Keep review authority separate from posting, approval and merge authority.

Does not establish: A valid empty findings list is not proof of safe code, and a reviewer has no implicit authority to publish comments or merge.

In technical terms

claude -p --output-format json headless execution exit status result envelope bounded permissions

Inspect the technical example

Actual CLI flags with a fictional supplied review packet; illustrative shell invocation, not a complete CI deployment

claude -p "Review the supplied change against its contract" --output-format json < review-packet.txt > review-result.json

Consumer checks, in order:
1. Process completed successfully.
2. Expected result envelope is present and reports an acceptable run outcome.
3. Review payload parses and passes its contract.
4. Findings have independently checked code evidence.

Read it as: The command runs noninteractively and requests JSON output. The application must still check process and envelope status before interpreting a payload. Configure bounded permissions and credentials separately.

Objective 4.1 · explicit criteria / inclusion/exclusion examples

In everyday language

Tell the reviewer what counts as a real defect and what does not. Require a concrete triggering input and consequence, not just severe wording.

Does not establish: Higher severity labels or a stricter output schema do not establish a finding is true.

In technical terms

explicit criteria inclusion/exclusion examples false positive precision evidence requirement

Inspect the technical example

Original review prompt excerpt — prompt text, not API configuration

Report only reachable violations of the supplied business contract.
Include: triggering input, current file/line, causal path, consequence.
Include: currency:null reaches an unintended USD charge default.
Exclude: harmless formatting and unsupported hypothetical callers.
If a required fact cannot be checked, state the evidence gap.

Read it as: The prompt defines acceptance criteria and evidence needs. It does not force a finding or substitute confidence for a demonstrated failure.

In everyday language

Choose the mechanism for the boundary you need: a machine-readable final response or valid arguments for a requested tool. Then check whether the values are actually supported.

Objective 4.4 · consumer validation / semantic validation

In everyday language

A receiver should reject the exact bad field, allow a limited evidence-based correction, and preserve unresolved cases rather than looping forever.

Does not establish: Retrying the same prompt or taking model consensus is not semantic validation. Never normalize unknown facts into fabricated values.

In technical terms

consumer validation semantic validation bounded retry field-level feedback quarantine

Inspect the technical example

Application validation/repair pseudocode — not reserved API fields

proposal = {total_minor:84.5, currency:"USD"}
errors = ["total_minor must be integer cents", "purchase_order key missing"]
feedback = {source:"EL-8 USD84.50; PO absent", errors:errors}
for attempt in bounded_repair_budget:
    revised = request_source_based_correction(feedback)
    if shape_valid(revised) and agrees_with_source(revised): return accepted(revised)
route_unresolved_to_review()

Read it as: The feedback includes both the defect and source evidence. A whole number such as 845 can still fail agreement with USD84.50. Retry conditions and maximum attempts are application choices.

Objective 4.5 · Message Batches / custom_id

In everyday language

A completed batch can contain different outcomes, and its result order need not match submission order. Keep identity and business acceptance separate.

Does not establish: Batch ended is not all-item success. API succeeded is not source-correct extraction, and a proposed tool call is not a local executor.

In technical terms

Message Batches custom_id processing_status succeeded errored canceled expired JSONL

Inspect the technical example

Actual batch result identity/outcome fields; message body omitted from this response excerpt

{"custom_id":"N-3-v1","result":{"type":"succeeded","message":{"role":"assistant","content":[{"type":"text","text":"..."}],"stop_reason":"end_turn"}}}

Illustrative consumer ledger:
N-3-v1 -> API succeeded -> business validation pending
N-1-v1 -> API errored -> inspect error cause
N-2-v1 -> API succeeded -> downstream accepted

Read it as: custom_id joins each response to its source/version. result.type is the per-request API outcome; processing_status is the batch-level state. The ledger’s validation states are application-defined.

Objective 4.6 · multi-pass review / local review

In everyday language

Different review passes should inspect different risks, then verify candidate findings against the actual code path. Repeating the same prompt does not make the result independent.

Does not establish: Majority agreement and a large shared context are not independent proof. A reviewer does not acquire merge authority by returning JSON.

In technical terms

multi-pass review local review integration pass candidate verification finding ledger

Inspect the technical example

Application review architecture pseudocode — not a built-in automatic certification mechanism

local = review_changed_files(diff, contracts)
integration = trace_cross_file_paths(diff, callers, fixtures)
candidates = merge_by_evidence(local, integration)
verified = reproduce_or_trace(candidates)
output = reconcile(verified, prior_findings)
# Omit resolved F1; retain still-supported F2; preserve run failures.

Read it as: Local checks can miss a defect formed by two changes together. Verification checks the proposed causal path; the ledger prevents both repeated resolved noise and silent loss of unresolved findings.

Keep a small working brief without losing the exact facts that decide the next action. A summary is useful only if critical uncertainty survives.

Objective 5.5 · calibration / held-out evaluation

In everyday language

Measure errors on the cases that matter and compare confidence with actual outcomes. A good average can hide a costly weak group, and the review queue needs an explicit overflow policy.

Does not establish: Model confidence is not automatically a calibrated probability; queue capacity is not evidence of correctness.

In technical terms

calibration held-out evaluation stratified metrics false positive/negative risk-based review capacity

Inspect the technical example

Application evaluation/routing pseudocode — thresholds are fictional and must be measured

compare(predicted_confidence, observed_correctness)
route_by(validated_risk_policy, measured_errors)
if required_reviews > available_capacity:
    keep_owned_pending_or_overflow_state()
# Do not silently relax a mandatory review requirement to empty the queue.

Read it as: Calibration asks whether claimed confidence agrees with outcomes, not whether the language sounds certain. Use separate evaluation data and inspect both error severity and reviewer capacity.

Objective 5.6 · provenance / claim-to-source mapping

In everyday language

Keep each claim attached to its source and time. A neat combined answer must not erase disagreement or pretend two systems have identical authority.

Does not establish: A unified query interface does not guarantee consistent records, and a citation does not establish that the cited source governs this field.
