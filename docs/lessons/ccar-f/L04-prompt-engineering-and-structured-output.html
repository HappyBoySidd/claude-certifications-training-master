CCAR-F Lesson 4 — Prompt Engineering and Structured Output (20%, about 12 questions)

Learning home and decision coach · Objective map · Application stories
Learn, decide and inspect a worked architecture example here

Understand the domain through its existing application cases, technical decisions and changed constraints.

No installation or API key is required for this reading and decision coach.

Plain ↔ technical: Mechanism examples and terminology · 4.1 · 4.2 · 4.3 · 4.4 · 4.5 · 4.6

Picture the application: An invoice arrives without a printed date, and the intake assistant produces a neat record containing an unsupported date. The expected result preserves what the document actually provides and makes missing information explicit. Prompt engineering, schemas and validation are the technical tools for controlling format without confusing it with factual correctness.

Stage 1 — A review flags everything that looks unusual

A marketing compliance reviewer flags any mention of price as a violation. The business actually forbids unsupported discount promises, not ordinary published pricing. The prompt says only “find risky copy.”

Original exam-style practice — choose ONE. Which prompt revision most directly improves precision without suppressing genuine violations?

A. Ask for fewer findings regardless of evidence.

B. Specify the violation criteria, require supporting text, and give contrasting compliant/noncompliant examples.

C. Tell the model to be absolutely certain without defining the rule.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. The model needs to know what counts as a problem. Include a compliant published price and an unsupported discount promise, with the reason for each. A hides real problems; C changes tone rather than the decision rule.

Follow the changed path:

copy + explicit criteria + examples → evidence-backed finding → reviewer checks rule fit

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Replay both examples and a new wording. Measure false positives and missed violations separately; a shorter report is not automatically a better report.

Changed-constraint decision — choose ONE before revealing: New documents put payment terms in footnotes. A: add representative input/output examples for varied layouts; B: add only more emphatic wording.

Reveal changed-constraint reasoning

A. Examples teach the mapping across layouts. Keep a genuine absence example so the system does not invent a field just to satisfy the demonstration.

Objective connections: 4.1, 4.2.

Stage 2 — The handoff parses, but the invoice is wrong

A document worker sends a record to an accounting application. It contains vendor, currency and total. The record is valid JSON, but says USD 900 while the invoice says USD 90. Here JSON is the container crossing this handoff; the business failure is the wrong extracted amount.

Original exam-style practice — choose ONE. Which receiving-side validation best prevents schema-valid but unsupported extracted values from reaching the downstream system?

A. Accept every record that parses as JSON.

B. Apply schema/type checks plus source-grounded semantic checks, preserve discrepancies and use bounded repair or review.

C. Ask the model for a higher confidence score and skip the source check.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. Check both the shape and meaning. A schema can verify a numeric amount field, but the source decides which amount is supported. A validates only the container; C does not provide independent evidence. Constrained output helps at its supported boundary; it does not make source facts true.

Follow the changed path:

invoice text → extracted record → shape check → source/amount check
wrong amount → specific feedback or review; supported value → eligible downstream record

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Use USD 90 and USD 900 test outputs against the same source. Both may pass type checks; only the supported amount may pass the business check. Preserve the source and failed value.

Changed-constraint decision — choose ONE before revealing: The vendor name is absent from all supplied material. A: keep retrying until one appears; B: mark unresolved and retrieve missing evidence or route to review.

Reveal changed-constraint reasoning

B. Retry can repair a reading error, not create absent evidence. Optional/nullable fields must match the business contract; do not silently waive a required business fact.

Objective connections: 4.3, 4.4.

Stage 3 — Ten thousand files finish with mixed outcomes

One invoice is easy to inspect. Overnight work now contains 10,000 independent files: 9,700 validate, 180 are unreadable, 100 hit transient service errors and 20 conflict with their sources. Those fictional ledger counts describe content/processing outcomes, not API status names.

Original exam-style practice — choose ONE. Which bulk-processing recovery design preserves completed work while making unresolved files visible?

A. Resubmit all 10,000 items whenever any result fails.

B. Join results by stable request IDs, keep per-item states, retry eligible transient failures within bounds, repair/quarantine bad inputs and reconcile downstream acknowledgements.

C. Mark the whole workload successful once the batch reports completion.

What is this asking? (optional, after reading the choices)

Identify the requirement that the current application fails to meet. Compare the proposed mechanisms against that requirement. Explain unfamiliar terms using the context above, then record a choice and your reason before opening the repair.

Reveal the repair and replay evidence

Choice B. The ledger lets you recover the 100 temporary failures without replaying 9,700 accepted items. The unreadable inputs need preparation; the conflicting records need evidence review. A risks duplicate downstream writes; C hides unresolved work. Batch results can arrive out of order.

Follow the changed path:

file ID → preparation → request ID → API outcome → output checks → downstream acknowledgement
unresolved item → retry / repair / quarantine; accepted item → retain checkpoint

The arrows show information or control moving between components; they do not imply that the model executes backend code itself.

Replay and inspect: Reconcile 9,700 + 180 + 100 + 20 = 10,000 before retries. After retries, count every item in exactly one current state and preserve attempt history. An API success still needs content validation.

Changed-constraint decision — choose ONE before revealing: The next job requires an answer in seconds. A: use asynchronous batch processing regardless of latency; B: select an interactive path with its own bounded recovery.

Reveal changed-constraint reasoning

B. Deadline and dependency shape the design. Batch is for eligible independent work that can wait; it does not replace interactive or ordered workflows.

4.0 The big idea

Plain ↔ technical · explicit criteria / inclusion/exclusion examples

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Tell the reviewer what counts as a real defect and what does not. Require a concrete triggering input and consequence, not just severe wording.

Does not establish: Higher severity labels or a stricter output schema do not establish a finding is true.

In technical terms

explicit criteria inclusion/exclusion examples false positive precision evidence requirement

Inspect the technical example

Original review prompt excerpt — prompt text, not API configuration

Report only reachable violations of the supplied business contract.
Include: triggering input, current file/line, causal path, consequence.
Include: currency:null reaches an unintended USD charge default.
Exclude: harmless formatting and unsupported hypothetical callers.
If a required fact cannot be checked, state the evidence gap.

Read it as: The prompt defines acceptance criteria and evidence needs. It does not force a finding or substitute confidence for a demonstrated failure.

Official mechanism reference

Vague instructions give vague results: name exact criteria and show 2–4 examples instead. For output a program will read, use a compatible schema-constrained interface for shape, then validate meaning against evidence and business rules. Tool selection alone does not ensure strict conformance. Deferred independent work may suit Batches only when dependencies, actual processing window and recovery fit its deadline.

4.1 Explicit criteria reduce false positives

Related technical reference · explicit criteria / inclusion/exclusion examples

  • "Flag comments only when claimed behavior contradicts the actual code" beats "check that comments are accurate".
  • "Be conservative" and "only report high-confidence findings" don't improve precision. Specific categories do.
  • A category with lots of false positives drags down trust in the accurate ones. Switch off the noisy category temporarily while you fix its prompt.
  • Define severity with concrete code examples for each level.

4.2 Few-shot examples

  • The most effective way to get consistent, actionable format when instructions alone vary.
  • Use 2–4 targeted examples of ambiguous cases, showing why one action beat the alternatives.
  • Show the format (location, issue, severity, suggested fix). Show acceptable patterns next to real issues. Show varied document structures (inline citations vs a bibliography).
  • They reduce made-up values and empty required fields in extraction, and they generalize to new cases.

4.3 Structured output through tool use

Related technical reference · explicit criteria / inclusion/exclusion examples

  • A declared tool input schema describes expected arguments. For enforced conformance use a supported strict/schema-constrained mode, and check exceptional outcomes; ordinary tool invocation is not an unconditional shape guarantee.
  • It does not remove semantic errors: line items that don't add up, or a value in the wrong field.
  • Today, not the exam: the API can go further with structured outputs (strict: true on a tool, or a JSON schema in output_config.format). Structured outputs guarantee the shape: the reply always matches your schema's fields and types. Two exceptions: a refusal, or a reply cut off at max_tokens, so check stop_reason. They don't guarantee the values are right, so still check the values in code (structured outputs, Tier 1, checked 2026-10-12). The saved objective emphasizes schema-based tool output; compare the actual stated constraints and supported interface rather than memorize a universal answer. See exam answer vs today.
  • tool_choice is the request setting that says whether Claude must call a tool: auto = Claude decides (text allowed), any = it must call some tool, a named tool = it must call that one (full table: Lesson 2, section 2.3). It's the add-on to tool use, for when no tool gets called or one must run first (exam guide, task 4.3). Use "any" when there are several schemas and the document type is unknown. Force {"type":"tool","name":"extract_metadata"} to make it run first.
  • Changed since the guide: on Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, any and forced tool return a 400 error. Use auto with strict: true on the tool, or output_config.format, in real code. On the exam, keep any / forced (tool use docs, Tier 1; see exam answer vs today). Model names change; check the models overview (checked 2026-10-21).
  • Schema design:
    • Make a field nullable/optional when the source may not have it, so the model doesn't invent a value to fill a required field.
    • Add "unclear" for ambiguous cases, and "other" plus a detail string for categories that need to grow.
    • Put format-normalization rules in the prompt as well as the schema.

4.4 Validate, retry, feed back

Related technical reference · explicit criteria / inclusion/exclusion examples

  • Retry with error feedback: send back the original document, the failed extraction and the specific validation errors.
  • Retries don't help when the information isn't in the source, for example when it's in an external document you didn't provide. They do help with format and structure errors.
  • Self-checking fields: calculated_total next to stated_total, and a conflict_detected flag.
  • A detected_pattern field lets you analyze false positives when developers dismiss findings.

4.5 Batch processing

Plain ↔ technical · Message Batches / custom_id

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A completed batch can contain different outcomes, and its result order need not match submission order. Keep identity and business acceptance separate.

Does not establish: Batch ended is not all-item success. API succeeded is not source-correct extraction, and a proposed tool call is not a local executor.

In technical terms

Message Batches custom_id processing_status succeeded errored canceled expired JSONL

Inspect the technical example

Actual batch result identity/outcome fields; message body omitted from this response excerpt

{"custom_id":"N-3-v1","result":{"type":"succeeded","message":{"role":"assistant","content":[{"type":"text","text":"..."}],"stop_reason":"end_turn"}}}

Illustrative consumer ledger:
N-3-v1 -> API succeeded -> business validation pending
N-1-v1 -> API errored -> inspect error cause
N-2-v1 -> API succeeded -> downstream accepted

Read it as: custom_id joins each response to its source/version. result.type is the per-request API outcome; processing_status is the batch-level state. The ledger’s validation states are application-defined.

Official mechanism reference

What a batch is. Think of a laundry service. You drop off a big bag, you pay about half what the express counter charges, and they promise it back within a day, but not at a set hour. You can't stand at the counter while they wash, and they won't phone you mid-wash to ask a question. The Message Batches API works the same way: you send many separate requests at once, Claude works through them when it can, and you collect the results later.

How it runs, in three steps.

  1. Submit one batch holding many requests, each with its own custom_id.
  2. Check the batch's status now and then (polling) until it says it has ended. The guide lists "polling for completion" as a batch feature (exam guide, technologies list). Polling tells you when it's done; it doesn't promise how soon.
  3. Download the results and match each one to its request by custom_id (exam guide, task 4.5).

Endpoint and field names for these steps are not printed in the guide: check the current docs (Message Batches, Tier 1).

The facts, in the guide's own words (official wording):

  • "The Message Batches API: 50% cost savings, up to 24-hour processing window, no guaranteed latency SLA" (exam guide, task 4.5)
  • Good for "non-blocking, latency-tolerant workloads (overnight reports, weekly audits, nightly test generation)" and "inappropriate for blocking workflows (pre-merge checks)" (exam guide, task 4.5)
  • "The batch API does not support multi-turn tool calling within a single request (cannot execute tools mid-request and return results)" (exam guide, task 4.5). Caveat: batches do support tools, including server tools that Anthropic runs; what they can't do is pause for your code's tool (Anthropic docs, Message Batches, Tier 1, checked 2026-10-12).
  • "custom_id fields for correlating batch request/response pairs" (exam guide, task 4.5)

"No guaranteed latency SLA" means no promised finish time. Each row is one question you might ask about it; the right column answers it.

QuestionAnswer
Where doesn't it fit?Blocking pre-merge checks, which need the synchronous API (the normal Messages API: you send one request and wait for the reply) (exam guide, task 4.5)
How do I match results to requests?custom_id on every request; resubmit only failed ids (exam guide, task 4.5)

Why no multi-turn tools. A normal agentic loop goes: Claude asks for a tool (stop_reason is "tool_use"), your code runs the tool, you send the result back, Claude continues. In a batch, nobody is on the line. The batch can't pause, come back to your code to run the tool, and pick up again. So any job that needs a tool loop (look something up, then decide) belongs on the synchronous API. Server tools, which Anthropic runs, do work in a batch (Anthropic docs, Message Batches, Tier 1, checked 2026-10-12). A one-shot job, such as "extract these fields from this document", fits a batch.

The 3-question decision test.

  1. Is someone waiting on the answer? A developer who can't merge, a customer in a chat, a pipeline step that blocks. If yes, use the synchronous API. Batch has no finish-time promise.
  2. Does your own code need to run a tool and send the result back partway through the request? If yes, use the synchronous API. Tools that Anthropic runs (server tools) are fine in a batch.
  3. Does your deadline still hold if the batch hits 24 hours and you have to resend the expired requests? If no, use the synchronous API.

Three "no, no, yes" answers mean batch it.

SLA window math, worked.

Nominal budget: interval + processing window + recovery/validation time ≤ deadline. Under the saved 24-hour-window assumption, SLA − 24 is a ceiling, not proof of delivery; pick an interval below it. The margin is for the resubmit: a batch can end at 24 hours with requests expired and no output, and those must be resent or run synchronously in time (Anthropic docs, Message Batches, Tier 1, checked 2026-10-12).

Your promise to the business: every document is processed within 30 hours of arriving. A batch can take up to 24 hours (exam guide, task 4.5). The worst case for a document is: it arrives just after a submission, waits for the next one, then that batch takes the full 24 hours.

  • Worst case = submission interval + 24 hours. It must be 30 hours or less.
  • So the ceiling is 30 − 24 = 6 hours. At exactly 6 there is no margin at all.
  • The saved guide's 4-hour window example illustrates nominal budgeting against a 30-hour target, not a production delivery guarantee (exam guide, task 4.5): 4 + 24 = 28 hours worst case, which leaves two hours remaining. That does not prove recovery fits: a failed/expired request may require a measured synchronous fallback or explicit incomplete outcome; another batch can take up to 24 hours too; Message Batches, Tier 1.
  • Try another: a 36-hour SLA: the ceiling is 12 hours, so submit every 8 hours or so to leave margin (see Drill 24 in CCAR-F hard drills).

Resubmit only the failures. Each request carries a custom_id you choose, such as the document's id. When results come back, match them by custom_id, not by order. Find the ones that failed, fix the cause (for example, split documents that were too long for the context window into chunks), and resubmit just those (exam guide, task 4.5). Don't rerun the whole batch.

Refine the prompt on a sample first, then run the full volume. A better first pass means fewer resubmissions (exam guide, task 4.5).

Quick check (done when you can answer all three without looking):

  • (a) A 48-hour SLA: what is the ceiling, and what interval would you pick?
  • (b) A nightly test-generation job that calls no tools: batch or synchronous?
  • (c) 40 of 1,000 requests failed. What do you resubmit?
Answers

(a) Ceiling 24 hours; pick less, for example 20, to leave a margin. (b) Batch. (c) Only the 40 failed custom_ids, after fixing the cause.

The batch traps are in the lesson's main Traps list below.

4.6 Multi-instance and multi-pass review

  • A model reviewing its own work in the same session keeps its reasoning and is less likely to question it. An independent instance does better than "review your work" or extended thinking (letting Claude reason step by step before answering).
  • Multi-pass: per-file passes for local issues, plus a cross-file integration pass for data flow.
  • A verification pass where each finding has its own confidence lets you route reviews by confidence.

Worked example

Related technical reference · explicit criteria / inclusion/exclusion examples

An extraction model sometimes fills invoice_date with a made-up date on invoices that don't have one. Answer: make invoice_date nullable (and add few-shot examples of documents without a date). Retries or "never make things up" in the prompt don't solve it, because the model is filling a required field.

Traps

Related technical reference · explicit criteria / inclusion/exclusion examples

  • "Add 'be conservative' to the review prompt."
  • "JSON mode (just asking for JSON in the prompt), or asking nicely, guarantees the schema." The saved guide describes schema-based output (wording: "eliminating JSON syntax errors"); verify strict-mode support and exceptional outcomes for actual enforcement, never the meaning.
  • "Use batches for the pre-merge check to save money."
  • "Retry until it finds the missing field."
  • Batch traps (4.5):
    • "Batch everything to save 50%." Wrong whenever someone is waiting on the answer.
    • "Polling or a fallback timer makes batch safe for blocking work." Neither creates a promised finish time; pick the synchronous API for blocking steps.
    • "Batch can't work because results come back unordered." Match results by custom_id.
    • "Batch an agent that calls tools step by step." Batch can't run tools mid-request.
    • "Resubmit the entire batch after some failures." Resubmit only the failed custom_ids, adjusted.
    • "Submit every 24 hours for a 30-hour SLA." Worst case is 48 hours. SLA − 24 is the ceiling; pick an interval below it.
    • (All exam guide, task 4.5.)
