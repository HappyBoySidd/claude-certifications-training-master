How to use this last-minute guide

Decision loop and whole-system picture

Plain ↔ technical · stop_reason / tool_use

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

In technical terms

stop_reason tool_use tool_result tool_use_id end_turn

Inspect the technical example

Actual Messages content-block shapes; fictional IDs/data; response and next-request excerpts, not a complete API request

Observed assistant response excerpt (stop_reason is RESPONSE metadata):
{"role":"assistant","stop_reason":"tool_use","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}

YOUR runtime executes the permitted lookup. For the next Messages request,
append only assistant role + content, followed by the matching result:
{"role":"assistant","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_order17","content":"{\"order_id\":\"O4\",\"status\":\"delivered\"}"}]}

Send the updated messages array in the next model request.
Do not copy response-only stop_reason into an input message.

Read it as: The tool_use id and tool_result tool_use_id must match. Input messages contain role and content; stop_reason describes the response. The returned content is observed lookup evidence, not a credit receipt.

Tool Design and MCP Integration - 18%

Plain ↔ technical · tools / name

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Give each capability a clear job, inputs and effect so the model can distinguish reading an order from changing its financial record.

Does not establish: A descriptive side-effect warning helps selection but is not an execution permission check.

In technical terms

tools name description input_schema required side effect

Inspect the technical example

Actual user-defined tool-definition shape; fictional read-only capability

{"name":"lookup_order","description":"Read delivery status for one order accessible to the current caller. Does not issue credits or change orders.","input_schema":{"type":"object","properties":{"order_id":{"type":"string","description":"Order identifier from the current case."}},"required":["order_id"],"additionalProperties":false}}

Read it as: name identifies the capability; description explains when to use it; input_schema constrains the arguments. Your runtime still enforces access.

Claude Code Configuration and Workflows - 20%

Plain ↔ technical · CLAUDE.md / nested instructions

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Keep stable team guidance in the project, specialized guidance near the relevant code, and personal preferences separate. Instruction text helps Claude reason; it is not an access-control setting.

Does not establish: A CLAUDE.md statement cannot enforce a permission like a runtime deny rule. Settings and instruction Markdown have different loading and enforcement roles.

In technical terms

CLAUDE.md nested instructions @imports instruction hierarchy .claude/settings.json

Inspect the technical example

Actual instruction-file locations and import syntax; fictional project layout

CLAUDE.md
  Preserve unknown monetary values; use the documented test command.
  @docs/financial-data-contract.md

src/importer/CLAUDE.md
  Importer-specific context and boundaries.

.claude/settings.json
  Runtime settings/permissions, separate from these Markdown instructions.

Read it as: CLAUDE.md contains instructions. @ imports another instruction source. Nested guidance is associated with a narrower code area; inspect which instructions actually loaded in the current working context.

Prompt Engineering and Structured Output - 20%

Plain ↔ technical · explicit criteria / inclusion/exclusion examples

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Tell the reviewer what counts as a real defect and what does not. Require a concrete triggering input and consequence, not just severe wording.

Does not establish: Higher severity labels or a stricter output schema do not establish a finding is true.

In technical terms

explicit criteria inclusion/exclusion examples false positive precision evidence requirement

Inspect the technical example

Original review prompt excerpt — prompt text, not API configuration

Report only reachable violations of the supplied business contract.
Include: triggering input, current file/line, causal path, consequence.
Include: currency:null reaches an unintended USD charge default.
Exclude: harmless formatting and unsupported hypothetical callers.
If a required fact cannot be checked, state the evidence gap.

Read it as: The prompt defines acceptance criteria and evidence needs. It does not force a finding or substitute confidence for a demonstrated failure.

Context Management and Reliability - 15%

Plain ↔ technical · context window / compaction

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Keep a small working brief without losing the exact facts that decide the next action. A summary is useful only if critical uncertainty survives.

Does not establish: A compacted conversation is not a refreshed policy or authorization record, and shortening text must not erase an unresolved payment.

In technical terms

context window compaction durable state decision-critical facts source pointers

Inspect the technical example

Application checkpoint/brief pseudocode — fields are authored business state

durable_case = {
  case_id:"C-41", requested_amount_minor:18720,
  approval:{amount_minor:6000, policy:"v3"},
  current_policy:"v4", operation:{id:"OP-6", status:"unknown"},
  sources:["booking:B-52", "approval:A-6"]
}
brief = select_next_decision_facts(durable_case)

Read it as: The brief retains exact amounts, approval scope and unknown effects while source pointers permit inspection. Compaction manages model context; the application owns durable business facts.
