Plain ↔ technical · stop_reason / tool_use

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

In technical terms

stop_reason tool_use tool_result tool_use_id end_turn

Inspect the technical example

Actual Messages content-block shapes; fictional IDs/data; response and next-request excerpts, not a complete API request

Observed assistant response excerpt (stop_reason is RESPONSE metadata):
{"role":"assistant","stop_reason":"tool_use","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}

YOUR runtime executes the permitted lookup. For the next Messages request,
append only assistant role + content, followed by the matching result:
{"role":"assistant","content":[{"type":"tool_use","id":"toolu_order17","name":"lookup_order","input":{"order_id":"O4"}}]}
{"role":"user","content":[{"type":"tool_result","tool_use_id":"toolu_order17","content":"{\"order_id\":\"O4\",\"status\":\"delivered\"}"}]}

Send the updated messages array in the next model request.
Do not copy response-only stop_reason into an input message.

Read it as: The tool_use id and tool_result tool_use_id must match. Input messages contain role and content; stop_reason describes the response. The returned content is observed lookup evidence, not a credit receipt.

Five-minute primer: how a Claude app works

Related technical reference · stop_reason / tool_use

New to the Claude API? Read this before the five rules below. Every later page builds on these few ideas.

  • One request, one reply. Your code sends Claude a request: a system prompt (standing instructions), the conversation so far, and a list of tools Claude may use. Claude sends back one reply. The reply says why Claude stopped, in a field called stop_reason: "end_turn" means it's finished; "tool_use" means it wants a tool run.
  • The API keeps no memory. "The Messages API is stateless, which means that you always send the full conversational history to the API" (Anthropic docs wording). Your application therefore manages coherent conversation state: preserve relevant messages, matched tool requests/results and critical facts, while budgeting or compacting older context deliberately. Stateless does not mean resend every raw byte forever.
  • A tool call: Claude asks, your code runs it. You describe each tool to Claude with a name, a description and an input schema (the shape its inputs must have). Claude never runs your tools; your code does. (Server tools such as web search are different: Anthropic runs those.) Claude replies with a tool_use block naming the tool and its inputs. Your code runs it and sends back a tool_result with the answer, matched by tool_use_id. Then Claude carries on.
  • An agent is that loop, repeated. Send, read stop_reason, run any tools, add the results to the history, send again, until an appropriate protocol outcome. This short example uses end_turn for normal model completion; truncation, refusal, paused/server-tool work and limits need separate handling. Model completion is not a transaction receipt. Lesson 1 teaches the loop.
  • One turn of the loop, worked through. A customer asks "Where's order 123?"
    1. Your code sends the question plus a lookup_order tool.
    2. Claude replies with stop_reason: "tool_use" and a tool_use block: lookup_order, input {"order_id": "123"}.
    3. Your code runs lookup_order("123") and sends back a tool_result ("shipped, arrives Tuesday") with the same tool_use_id, plus the whole history.
    4. Claude replies with stop_reason: "end_turn": "Your order has shipped and arrives Tuesday." Your code stops.
  • Three names you'll see on every page:
    • Claude Agent SDK: a library that runs the agent loop for you, with subagents, hooks and permissions built in.
    • Claude Code: Anthropic's coding agent. It works in your project, reads files such as CLAUDE.md, and can run in CI with nobody at the keyboard. Lesson 3 covers its setup.
    • MCP (Model Context Protocol): an open standard for plugging tools and data into Claude through a small server. Lesson 2 covers it.

Saved blueprint and current implementation. Use the saved guide to locate objectives, and current primary documentation to validate runtime behavior. Solve the conditions actually stated in a question; do not memorize “always choose X.” Where terminology has changed, consult documented differences, checking the supported interface rather than assuming a universal exam answer.

Words used on every page:

  • Message: one user or assistant entry in history. A turn can span several model/tool exchanges; check the protocol rather than counting visible messages.
  • Token: a small chunk of text (a word, part of a word or a character); size limits and prices are counted in tokens (glossary, Tier 1).
  • Agent: Claude running in a loop, calling tools until a job is done.
  • Tool: a function you give Claude that it can ask to run (for example get_customer).
  • Coordinator / subagent: the main agent that splits up the work / a helper agent it starts for one piece.
  • Hook: your own code that runs automatically before or after a tool call, and can block or change it.
  • Prerequisite gate: code that blocks a tool until an earlier step has succeeded (for example, no refund until the customer is verified).
  • Schema: a description of the exact shape the output must have (which fields, which types).
  • Few-shot examples: a few sample inputs with the right outputs, put in the prompt to show Claude what you want.
  • Context (window): all the text Claude can work with in one request: the instructions, the history, the tool results, and the reply it is writing. It has a size limit.
  • Synchronous: you send a request and wait for the answer right away.
  • CI: the automatic system that builds and tests code on every change, with nobody at the keyboard.

Five decision habits — apply the stated constraint

Related technical reference · stop_reason / tool_use

  1. Enforce mandatory rules at the executable boundary. A prompt can guide interpretation; a pre-effect service guard checks identity, authority and policy before a mutation. Correct code still needs trustworthy data, tested predicates and coverage of all mutation paths. Post-action normalization cannot prevent a completed effect.
  2. Make judgment criteria explicit. Relevant examples and clear severity/evidence criteria help when the task requires model judgment. A schema or hook is not a replacement for understanding what the judgment means.
  3. Separate shape, truth and completion. Compatible strict schema constraints govern structure; source/business validation checks meaning; a correlated result or receipt establishes the relevant outcome. None implies the others.
  4. Scope capabilities by the task. Give a specialist the smallest sufficient set of tools and a self-contained brief. The guide's small-versus-large tool-count example is an illustration, not a universal quota.
  5. Diagnose before increasing resources or retrying. Protocol outcomes govern normal continuation/completion. Keep turn, cost and time safety budgets; exhausting one means interruption or handoff. More context, another model or a retry may help a diagnosed bottleneck, but cannot substitute for missing authority or evidence.

Self-check

  • Which domain is the biggest? (Agentic Architecture, 27%)
  • Why does "add it to the system prompt" usually lose to "add a hook"? (Choose a tested pre-effect executable check for a mandatory predicate; prompt guidance alone cannot enforce it. Check hook timing, failure handling and bypass paths.)
  • Which two scenarios mostly test Claude Code? (2 and 5)
  • Claude's reply has stop_reason: "tool_use". What does your code do next? (Run the tool, send a tool_result with the matching tool_use_id plus the full history, and call again.)
