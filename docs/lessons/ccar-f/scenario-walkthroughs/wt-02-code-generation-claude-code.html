The whole job in one chart

Plain ↔ technical · Glob / Grep

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

First find the relevant files, then inspect their contents, and only then make a small change. Tool names describe different jobs, not interchangeable ways to guess what a repository contains.

Does not establish: A search hit is not the whole implementation, and a successful edit is not a successful test or deployed change.

In technical terms

Glob Grep Read Edit Write Bash targeted exploration

Inspect the technical example

Claude Code tool workflow pseudocode — semantic jobs, not tool-call JSON signatures

Glob: locate **/importer.py and related test paths
Grep: find deposit uses and report-formatting callers
Read: inspect current importer, formatter and relevant fixtures
Edit: change the specific proven boundary
Bash: run the relevant check and capture its actual outcome

Read it as: Glob locates paths; Grep locates matching content; Read supplies current code evidence. An Edit changes a known region; Write can replace file content and therefore needs a justified scope.

  • You decide: for each rule or convention, where should it go?
  • Design rule:
    • Team-wide conventions → the project CLAUDE.md, checked into git [Guide 3.1]. A personal ~/.claude/CLAUDE.md is not shared with teammates.
    • Rules for one file type spread across folders (tests, Terraform) → a file in .claude/rules/ with paths: in its front matter. It loads only when matching files are touched [Guide 3.3].
    • A rule that must hold every time (never edit migrations/) → a hook or a permission rule, not a sentence in CLAUDE.md. Hooks give "deterministic guarantees" (exam wording) [Guide 1.5].

Run it for real: 10 what-if questions

Related technical reference · Glob / Grep

These are project-written practice questions, not real exam questions. Each was checked against the exam guide's 12 sample questions so none repeats one.

1. A new hire's Claude Code doesn't follow the team's naming rules. Everyone else's does. What's the likely cause?

The rules live in other people's personal ~/.claude/CLAUDE.md, not in the project CLAUDE.md in git. Move them into the project file [Guide 3.1].

Repair tags: Objective 3.1. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

2. Your CLAUDE.md says "NEVER edit files in generated/" in capitals. Claude still did it twice this week. What's the fix?

A PreToolUse hook (or a deny permission rule) that blocks Edit and Write on generated/. A prompt instruction is probabilistic; a hook is deterministic [Guide 1.5].

Repair tags: Objective 1.5. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

3. Your block-hook script prints "blocked" and exits 1. The edit still happens. Why?

With plain-text output, exit 1 is a non-blocking error in Claude Code, so the edit goes ahead. To block, exit 2, or print JSON with hookSpecificOutput.permissionDecision: "deny" and a permissionDecisionReason (Claude Code hooks docs, see conditions and errors, section 7). A hook gives a deterministic block where a prompt can't [Guide 1.5].

Repair tags: Objective 1.5. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

4. The task is "rename one variable in one file, stack trace attached". Plan mode or direct?

Direct execution. It's small and the scope is clear [Guide 3.4]. Plan mode is for big, open changes across many files.

Repair tags: Objective 3.4. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

5. You explain a date-formatting change in prose three times; Claude interprets it differently each time. What now?

Give 2 to 3 concrete input/output examples ("2026-03-04T10:00Z → 4 Mar 2026"). Examples beat prose when wording is read inconsistently [Guide 3.5].

Repair tags: Objective 3.5. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

6. You have a .claude/rules/terraform.md file with paths: ["**/*.tf"]. A tool writes generated .tf files into infra/generated/, and those must not follow the hand-written conventions. Claude keeps applying them there. What do you change?

The paths: patterns. A path rule loads only for files that match its patterns [Guide 3.3], and **/*.tf matches everything. List only the folders where the conventions belong, for example infra/modules/**/*.tf and services/*/deploy/**/*.tf.

Repair tags: Objective 3.3. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

7. A codebase-analysis skill dumps 20,000 tokens into the main chat every time. What front matter fixes that?

context: fork, which runs the skill in an isolated sub-agent and returns only the result [Guide 3.2].

Repair tags: Objective 3.2. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

8. You resume yesterday's session, but since then a teammate merged 30 changed files. Claude keeps quoting old code. What should you have done?

Started a new session with a structured summary, because the earlier tool results were stale. Resume only when most earlier reads are still true, and then name the files that changed [Guide 1.7].

Repair tags: Objective 1.7. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

9. Edit fails with "text not unique" because the same line appears 4 times, and you only want to change the third one. What's the exam answer?

Read the whole file, then Write it back with the change [Guide 2.5]. (In real work today, a longer old_string that includes surrounding lines also works (practice, not doc). See exam answer vs today.)

Repair tags: Objective 2.5. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

10. You want to try two different refactoring strategies from the same analysis and compare them. How?

Fork the session (fork_session) twice from the shared starting point, one branch per strategy [Guide 1.7]. Each branch starts from the same baseline, so neither sees the other's attempt (practice, not doc: the guide states the fork, not this reason).

In real life: beyond the exam (not exam rules, open when you want the real-world view)

In real life (beyond the exam)

Related technical reference · Glob / Grep

Beyond the exam. This is real-world best practice. Where it differs from the exam guide, this page's exam answer wins on exam day. A line marked (practice, not doc) is a habit teams use; no Anthropic page states it as a rule. Anthropic pages checked 2026-10-09.

The exam picture is a team using Claude Code to write, refactor, debug and document code, with CLAUDE.md, shared commands and a choice between plan mode and direct execution [Guide, Scenario 2].

Where you meet this at work

  • A payments repo where migrations must not be edited. That rule is a hook or a permission deny, not a sentence in CLAUDE.md. Same split as Walkthrough 2, Step 1.
  • A mobile team with an "add a screen" skill. The skill lives in the repo so a new hire gets it. A command that exists only in one person's home folder does not travel (Step 2).
  • A library upgrade across dozens of files. Plan mode, because there are many valid approaches (Step 3). A one-line null check stays direct execution.
  • A data-pipeline repo that must stay formatted. A PostToolUse hook on Edit and Write runs the formatter and sends failures back to Claude (Step 5).

What production adds

  1. Two people "fix" the same rule in two places, and they drift. Design move: team conventions live in the project CLAUDE.md in git [Guide 3.1]. A personal ~/.claude/CLAUDE.md is not the team source.
  2. A skill that can run the shell can also run a dangerous command. Exam answer: allowed-tools in the skill's front matter (the short header at the top of the skill file) limits tools during the skill [Guide 3.2]. Today: allowed-tools only pre-approves tools. disallowed-tools is what blocks them. On the exam, pick allowed-tools. See exam answer vs today. Skills.
  3. A hook you trust is silently off. Exit code 1 does not block a PreToolUse hook. Exit code 2 does (Walkthrough 2, Step 5). Hooks. Design move: run the hook against a forbidden path in a scratch repo before you rely on it (practice, not doc).
  4. The session that wrote the change is a weak reviewer of that change. A separate instance reviews it [Guide 4.6]. A person reviewing the diff is a team habit (practice, not doc).
  5. Tomorrow's session trusts yesterday's file reads after someone else merged. Design move: if the code changed a lot, start a new session with a structured summary. Do not resume a stale one [Guide 1.7].
  6. Test rules eat context on every unrelated task. Design move: put them in .claude/rules/ with paths:, so they load when those files are touched [Guide 3.3].

An architect's checklist

  • Are team conventions in the project CLAUDE.md in git? [Guide 3.1]
  • Is "never edit this folder" a hook [Guide 1.5], or a permission deny (practice, not doc)?
  • Do many-file changes start in plan mode? [Guide 3.4]
  • If Edit fails because the text is not unique, do you Read the file and then Write it? [Guide 2.5] Today, Edit can also take replace_all when every copy should change. On the exam, pick Read + Write. See exam answer vs today.
  • Do shared tasks live in .claude/commands/ or .claude/skills/ in the repo? [Guide 3.2]
  • Can you see which memory files loaded? On the exam, that command is /memory [Guide 3.1].

Two real-life what-ifs

1. Extends Step 1. A contractor's Claude Code rewrites a file under migrations/ even though CLAUDE.md says not to. What is missing?

A sentence in CLAUDE.md is not a guarantee. Block that path in code: a hook [Guide 1.5], or a permission deny (practice, not doc).

2. Extends Steps 3 and 6. A login function throws. The stack trace points at one file. A teammate still wants plan mode before anyone edits. What do you choose?

This is one known bug in one file, and the trace is already attached. Use direct execution [Guide 3.4].
