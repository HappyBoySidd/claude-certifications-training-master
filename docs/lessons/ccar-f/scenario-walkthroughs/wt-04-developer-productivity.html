The job (from the exam guide v1.0, Tier 1, paraphrased): an Agent SDK tool helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and connects to MCP servers.

Step 2. Find the right files

  • You decide: Glob or Grep?
  • Design rule (exam wording): Glob for "file path pattern matching" (for example **/*.test.tsx); Grep for "content search" (function names, error messages, imports) [Guide 2.5].
  • What changed since: today Glob and Grep are off by default on macOS, Linux and WSL; Claude searches through Bash, and naming them in --tools or --allowedTools brings them back. On the exam: pick Glob for names, Grep for content.
  • What can go wrong:
What went wrongSignal you seeWhat the design does
Glob used to find callersmatches files named *refund*, misses the real callersGrep for the call text [Guide 2.5].
Grep used to find a file typenoisy content matches instead of a file listGlob with a name pattern [Guide 2.5].

Step 3. Read selectively and trace

  • You decide: whole files, or slices?
  • Design rule: find entry points with Grep, then Read to follow imports "rather than reading all files upfront" (exam wording) [Guide 2.5]. For a wrapper module, list every name it exports, then Grep for each one [Guide 2.5].
  • What can go wrong:
What went wrongSignal you seeWhat the design does
Whole large files read firstcontext fills before the real question startsGrep for the entry point, then Read only that part [Guide 2.5].
A wrapper hides real usageGrep for the wrapper finds only import linesList every name it exports, then Grep for each one [Guide 2.5].

  • You decide: which server, configured where, and how does Claude know to use it?
  • Design rule:

    • Read-only catalogs (issue lists, schemas) → expose them as MCP resources [Guide 2.4].

Run it for real: 10 what-if questions

These are project-written practice questions, not real exam questions. Each was checked against the exam guide's 12 sample questions so none repeats one.

1. You need every place that calls applyRefund(. The agent runs Glob for *refund*. What's wrong?

Glob only matches file names. Callers are found by content, so use Grep for applyRefund( [Guide 2.5].

Repair tags: Objective 2.5. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

2. First question in a repo you've never seen: "where does refund logic live?" The agent's very first move is a search for "refund", which returns 900 matches across tests, fixtures and docs. What should have come first?

The map first. CLAUDE.md holds the project's own instructions and context [Guide 3.1]. Reading it, the README and the top-level folders before any wide search, then searching inside the folder that matters, is a house habit (practice, not doc).

Repair tags: Objective 3.1. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

3. You describe the new reason code in prose. Claude adds it to the enum but registers it differently from every existing code, and misses the test. What's the quickest way to get it right?

Show one concrete example: an existing reason code end to end (enum entry, where it's registered, its test), and ask for the new one in the same shape. Examples beat prose when wording is read inconsistently [Guide 3.5].

Repair tags: Objective 3.5. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

4. Two hours into exploring, the agent starts saying "this probably uses a standard repository pattern" instead of naming the classes it found earlier. What's happening, and what helps?

Context degradation over a long session [Guide 5.4]. Use a scratchpad of findings it re-reads, send broad questions to subagents, and /compact.

Repair tags: Objective 5.4. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

5. A teammate clones the repo. The shared database MCP server in the repo's .mcp.json works for everyone else, but no tools from it appear in their session. One person says copy the server into their user config; another says their token must be missing. What do you tell them?

Inspect the actual connection, approval and discovery state before choosing a cause. Project-scoped configuration requires the user's approval; a pending approval is one possible cause. Authentication or initial discovery failures can also prevent tools from appearing. Check /mcp and claude mcp list, resolve the observed failure and reconnect or retry discovery as appropriate. Keep the shared server in project .mcp.json rather than copying it into user configuration merely to bypass diagnosis [Guide 2.4]. Current MCP connection and scope documentation (Tier 1, checked 2026-10-14).

Repair tags: Objective 2.4. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

6. The GitHub MCP server loads, but every call fails with an auth error. .mcp.json has ${GITHUB_TOKEN}. What's likely?

A missing, expired or insufficiently scoped credential is a hypothesis, not a confirmed cause. Inspect the actual server configuration and credential source, then fix the observed authentication failure without printing the secret. For ordinary unset ${VAR} references without defaults, current Claude Code warns and retains unexpanded text; some credential variables in remote url/headers instead expand as empty without a warning. Do not generalize one transport's behavior to every server. Set or refresh the correct credential, reconnect, and verify an authorized call [Guide 2.4]. Current environment expansion exceptions (Tier 1, checked 2026-10-14).

Repair tags: Objective 2.4. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

7. You built a great search_codebase MCP tool, but the agent keeps using built-in Grep. What do you fix first?

The MCP tool's description: say what it does better and when to use it instead of Grep [Guide 2.4]. Fix descriptions before adding routing logic.

Repair tags: Objective 2.4. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

8. The agent makes many exploratory calls just to learn which Jira projects exist. What's a better design?

Expose the list of projects as an MCP resource, so the agent can see what exists without making exploratory tool calls [Guide 2.4].

Repair tags: Objective 2.4. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

9. Every Friday a developer pastes the same 40-line release checklist into Claude Code. Each run dumps pages of output into the main chat. What should the team build?

A skill in .claude/skills/, shared through git, with context: fork so the long output stays in its own sub-agent and only the result comes back [Guide 3.2]. It's an on-demand workflow, so it doesn't belong in CLAUDE.md, which loads every session.

Repair tags: Objective 3.2. author-proposed from explicit source Guide tags. These tags do not certify full skill coverage.

10. A search tool returns 40,000 tokens of log lines. What do you change?

Make the tool page, filter and return only the fields needed. Claude Code warns above 10,000 tokens of MCP output and caps it at 25,000 by default. Trimming also protects context [Guide 5.1].

In real life: beyond the exam (not exam rules, open when you want the real-world view)

In real life (beyond the exam)

Related technical reference · session_id / resume

Beyond the exam. This is real-world best practice. Where it differs from the exam guide, this page's exam answer wins on exam day. A line marked (practice, not doc) is a habit teams use; no Anthropic page states it as a rule. Anthropic pages checked 2026-10-09.

The exam picture is an assistant that helps an engineer explore a codebase, understand old code, generate boilerplate and automate repeated tasks, using Read, Write, Bash, Grep and Glob, plus MCP servers [Guide, Scenario 4].

Where you meet this at work

  • A new engineer on a ten-year billing repo. They read CLAUDE.md, the README and the top folders before a wide search (Walkthrough 4, Step 1, practice). Callers of a function are a Grep, not a Glob on the file name [Guide 2.5].
  • "Which test files match this path?" versus "where is this error string?" Glob for the path pattern. Grep for the text [Guide 2.5]. On the exam, that split is the answer. The walkthrough notes a product change about those tools defaulting off. Follow WT-04 for that note. Do not treat it as a new exam answer.
  • Tickets and pull requests from an existing MCP server. Use a community server for a standard system. Put the token in an environment variable, not in the file [Guide 2.4].
  • A small new endpoint versus a cross-cutting rename. The endpoint can be direct execution. The rename is plan mode [Guide 3.4].

What production adds

  1. A token gets committed in .mcp.json. Design move: reference it as ${GITHUB_TOKEN} (or the variable you actually use) and keep the value in the secret store [Guide 2.4]. A project server the whole team needs is committed. A personal experiment stays in that person's own settings (user scope), not in the shared project file [Guide 2.4].
  2. Claude keeps using Grep when you built a better MCP tool. Design move: rewrite that tool's description so it says when to use it instead of Grep [Guide 2.1, 2.4].
  3. Ticket text and README text can carry hidden instructions. Design move: same untrusted-content rule as Walkthrough 1. The agent that reads tickets should not also hold production deploy tools. Mitigate jailbreaks.
  4. A "find every caller" question floods the main session. Design move: hand broad discovery to a subagent that returns a short summary, keep a scratchpad of entry points, and use /compact when the session fills [Guide 3.4, 5.4].
  5. One agent is handed every tool you own. Design move: about four or five tools for that role [Guide 2.3]. Read-only catalogs (issue lists, schemas) can be MCP resources rather than tools that take actions [Guide 2.4].
  6. Generated code merges with no person looking. A separate instance reviews the change [Guide 4.6]. A person reviews the diff before merge (practice, not doc).

An architect's checklist

  • For a content search, is the tool Grep, and for a path pattern, Glob? [Guide 2.5]
  • Does broad discovery return a summary instead of dumping every file into the main session? [Guide 5.4]
  • Is the shared MCP server in project .mcp.json, with secrets outside the file? [Guide 2.4]
  • If Claude ignores your MCP tool, did you fix the description before adding more prompt text? [Guide 2.4]
  • Does each agent get a small tool set for its role? [Guide 2.3]
  • Is a many-file change in plan mode, and a one-file fix in direct execution? [Guide 3.4]
  • Does a person see the diff before generated code merges? (practice, not doc)

Two real-life what-ifs

1. Extends Step 2. You need every test file whose name ends in .test.tsx, in any folder. The agent searches the file contents for the words test and tsx and comes back with almost nothing. What do you change?

That need is a path pattern. Use Glob [Guide 2.5].

2. Extends Step 5. A teammate pastes a personal-access token into .mcp.json and commits it so "CI will work." The server is a shared issue tracker. What do you change?

Take the token out of the file. Reference an environment variable with ${VAR} syntax [Guide 2.4].
