What this file is

Most study pages answer "which option?" in one look. This file goes one level down. It walks each system the way you would build it in code. Every step says:

  • Checks: what the code looks at.
  • Results: each possible answer, and where it sends you next.
  • Exact: the field, code, flag or setting, word for word, with its source in brackets.
  • Right / Wrong: what a right exam answer at this step looks like, and the tempting wrong one.

Some exam questions show you a message, a config file or a hook script and ask "what happens next?" or "what is broken?". These flows are how you answer those fast.

Exam answer vs today's docs. The exam guide is version 1.0 from July 2026. Where today's docs say something different, you get the exam's answer first, then a short "What changed since" note that ends with what to pick on the exam.

Background, not tested. The exam guide's Out-of-Scope list includes API authentication, billing, rate limiting and quotas. Lines marked "background, not tested" are there so the code makes sense. Don't spend study time on them.

Source tags used below. [Guide 4.3] means the official exam guide, task statement 4.3 (the exact exam wording). Doc tags like [errors] are links listed at the bottom of the page. (practice, not doc) means a common design habit the exam tests but no Anthropic page states as a rule.

Flow 1: How does an extraction pipeline decide what a person checks?

Plain ↔ technical · stop_reason / tool_use

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Claude asks to look up an order. Your program performs the lookup, sends its observed result back, and asks Claude to continue. Stopping the model is separate from proving a payment finished.

Does not establish: tool_use is a request for client execution, not execution itself; end_turn is not business settlement.

stop_reason tool_use tool_result tool_use_id end_turn

Step 1. Authenticate

  • Checks: the API response status before anything else.
  • Results (background, not tested):
    • 401 authentication_error (bad, revoked or expired key) → stop, alert a person. A retry cannot fix it. [errors]
    • 403 permission_error (key lacks access) → stop, fix access. [errors]
    • Works → Step 2.
  • Tested part: where the secret lives (next bullet). That is TS 2.4.
  • Exact: the key comes from an environment variable or a secret store, never from code or the repo. MCP servers get secrets with ${VAR} expansion in .mcp.json, for example ${GITHUB_TOKEN}. [Guide 2.4] [mcp]
  • Right: "Read the key from an environment variable; on 401, fail fast and alert."
  • Wrong: "Retry 401 with exponential backoff." Backoff is for 429, 500, 529. A bad key never heals. (Background, not tested: a 429 with no retry-after header may be a tier spend cap, which keeps failing until access resumes, so fail and alert. A spend limit you set yourself returns a 400, not a 429. [errors])

Step 2. Pick the API by who is waiting

  • Checks: is a person or a pipeline blocked until the answer comes back?
  • Results:
    • Yes (a user is waiting, a merge is blocked) → synchronous Messages API.
    • No (overnight report, weekly audit, a big backlog) → Message Batches API.
  • Exact:
    • Batch: 50% cost savings, up to 24-hour processing window, no guaranteed latency SLA (exam wording). [Guide 4.5]
    • A batch holds up to 100,000 requests or 256 MB, whichever comes first. Results stay for 29 days. [batch]
    • Each request has a custom_id: 1 to 64 letters, digits, - or _. Results can come back in any order, so you match on custom_id. [batch]
    • Each result is succeeded, errored, canceled or expired. [batch]
    • Batch does not support multi-turn tool calling within a single request (cannot execute tools mid-request and return results) (exam wording). [Guide 4.5] What that means: a batch request can carry a multi-turn message history, and server tools run inside it. What it can't do is stop for your tool, wait for your result, and carry on in the same request. [batch]
  • Timing math (exam skill): the rule is cycle + 24 h + safety margin ≤ deadline. With a 30-hour promise and batches that can take up to 24 hours, submit every 4 hours, not 6 (6 is the ceiling: 30 − 24): 4 + 24 = 28, which leaves 2 hours of safety margin (most batches finish within an hour, but a resend can take up to 24 hours too). Expired requests return no output, so the margin must cover resubmitting them or running them synchronously (Anthropic docs, Message Batches, Tier 1, checked 2026-10-12). A 6-hour cycle hits exactly 30 with no room. This matches the guide's own example, 4-hour windows to guarantee 30-hour SLA with 24-hour batch processing (exam wording). [Guide 4.5]
  • Right: "Nightly batch for the backlog; synchronous calls for the upload screen."
  • Wrong: "Batch everything to save 50%", including a blocking step. Or "use Batch for a loop that needs tool results mid-request".

Step 3. Prepare the input by file type

  • Checks: what kind of file is this?
  • Results:
    • Plain text → send the text.
    • Any PDF, digital or scanned → a PDF document block. Each page is read as text plus an image of the page, so a digital PDF isn't text only. [pdf]
    • Photo → an image block, or OCR first.
    • Keep this short in your head: image analysis itself is on the guide's Out-of-Scope list.
    • Poor scan → expect lower certainty. Ask for a confidence value per field, not one score per document.
    • Word or Excel → convert to PDF or text first (practice, not doc).
  • Right: "Ask for field-level confidence so the review step can route by field." [Guide 5.5]
  • Wrong: "One overall confidence score for the document." It hides which field is unreliable.

Step 4. Call with an extraction tool and a JSON schema

  • Checks: how do we make sure the reply is JSON in our shape?
  • Results (most reliable first):
    1. A tool whose input_schema is your JSON schema. This is the exam's answer. Add tool_choice only if Claude sometimes answers in text. [Guide 4.3]
    2. "Reply only in JSON" in the prompt: can break syntax.
    3. Prefilling the reply with {: weakest.
  • Exact (exam wording, [Guide 4.3] and [Guide 2.3]):
    • tool_choice: "auto": model may return text instead of calling a tool.
    • tool_choice: "any": model must call a tool but can choose which. Use it when several extraction schemas exist and the document type is unknown.
    • tool_choice: {"type": "tool", "name": "extract_metadata"}: model must call a specific named tool. Use it to make one step run first (for example metadata before enrichment), then do later steps in follow-up turns.
    • Read the data from the tool_use block's input field. [handle-tools]
  • What changed since: today you can add strict: true to the tool to guarantee the shape, or use JSON outputs with output_config.format. [structured] On Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, any and a forced tool_choice (a named tool) return a 400, so today's docs say use auto with strict: true. Manual extended thinking also blocks any and a named tool. [define-tools] Prefill is gone too: on Claude 4.6 and later models, a prefilled last assistant message returns a 400 invalid_request_error ("This model does not support assistant message prefill"). [errors] See exam answer vs today. On the exam: pick tool use with a JSON schema. Add tool_choice (any, or the named tool) only when no tool gets called or one must run first. Rank prefill last.
  • Right: "Define extract_invoice with the schema as its input_schema. If Claude sometimes replies in text instead, add tool_choice."
  • Wrong: "Add 'respond only with valid JSON' to the system prompt." Or "use a bigger model."

Step 5. Design the schema so Claude never has to invent

  • Checks: can every required field always be filled honestly from the source?
  • Results:
    • Field is always in the document → required, normal type.
    • Field may be missing → make it nullable, for example "type": ["string", "null"] (allowed in strict schemas; anyOf with a null branch also works) [structured], and say "use null if not present". Designing schema fields as optional (nullable) ... preventing the model from fabricating values to satisfy required fields (exam wording). [Guide 4.3]
    • Category list may grow → enum plus "other" and a free-text detail field. Add "unclear" for ambiguous cases. [Guide 4.3]
    • Formats vary (dates, currencies) → put format rules in the prompt next to the strict schema. [Guide 4.3]
  • Exact: a strict schema stops syntax errors. It does not stop meaning errors, such as line items that don't add up to the total or a value in the wrong field. [Guide 4.3] Today's structured outputs also don't support minimum, maximum, multipleOf, minLength, maxLength. Some SDK helpers strip them and re-check them after the reply; not every helper validates (the TypeScript JSON-schema helper doesn't, and Java rejects them). So check ranges in your own code. [structured]
  • Right: "Make po_number nullable so the model can return null when the receipt has none."
  • Wrong: "Keep it required and add 'never leave fields blank'." That pushes the model to make one up.

Step 6. Check the schema in code, retry with the exact error

  • Checks: run a JSON Schema validator on the tool input.
  • Results:
    • Pass → Step 7.
    • Fail → retry. The follow-up includes the original document, the failed extraction, and specific validation errors (exam wording). Cap the retries (for example at most 2 retries). Still failing → human review. [Guide 4.4]
    • No tool call at all (under auto, Claude replied in text) → retry with feedback asking it to call the tool; this uses one of the same retries. [define-tools]
  • The limit of retry: retries fix format and structure errors. They don't fix data that is not in the document (for example, it lives in a separate file you never sent). [Guide 4.4]
  • Right: "Retry with the validator's exact message, for example line_items[2].amount: expected number."
  • Wrong: "Retry with 'please try again'", or "retry five times hoping the missing PO number appears".

Step 7. Check meaning in code

  • Checks: do the numbers agree with each other?
  • Results:
    • Ask the model for both stated_total (as printed) and calculated_total (sum of lines), plus a conflict_detected boolean. These field names are exam wording. [Guide 4.4]
    • Your code adds the lines too. Match → Step 8.
    • Mismatch → retry once with the specific mismatch (it may be a misread digit). Still off → keep both values, flag the field, send to review. Never overwrite the printed total.
  • Right: "Extract both totals and flag the conflict for a reviewer."
  • Wrong: "Tell the model to make the totals match." That teaches it to fake data.

Step 8. Route to review

  • Checks: is this extraction risky?
  • Results: send to a person when any field's confidence is under its threshold, a required field is null, totals conflict, or the source is ambiguous or contradictory. Everything else is auto-accepted.
  • Exact (exam wording, [Guide 5.5]):
    • Field-level confidence scores calibrated using labeled validation sets.
    • Stratified random sampling for measuring error rates in high-confidence extractions and detecting novel error patterns.
    • aggregate accuracy metrics (e.g., 97% overall) may mask poor performance on specific document types or fields. Check accuracy by document type and by field before cutting human review.
  • Right: "Route low-confidence fields to reviewers; stratified-sample the auto-accepted ones by document type."
  • Wrong: "97% overall, so remove human review." Or "review a plain random 5% of everything." Or "trust the model's raw confidence without calibrating it against labeled data."

Step 9. Close the loop

  • Checks: what kinds of errors keep happening?
  • Results: log each error with document type, field and error type. Add a detected_pattern field: Adding detected_pattern fields to structured findings to enable analysis of false positive patterns when developers dismiss findings (exam wording). [Guide 4.4] Fix the schema, prompt or few-shot examples from the pattern.
  • Few-shot rule: 2 to 4 targeted examples, showing varied document layouts, fix empty or null extraction of required fields. [Guide 4.2] Write explicit criteria, not "be conservative". [Guide 4.1]
  • Before a big batch: refine the prompt on a sample set first, so the big run passes first time. [Guide 4.5]
  • On batch failures: resubmit only the failed ones by custom_id, changed as needed (for example, split a document that was too long). [Guide 4.5]

Step 1. Build the request with the full history

  • Checks: does messages hold every earlier turn, including every tool_use and tool_result?
  • Results: yes → call. No → the model loses track. The API keeps no memory between calls; you send complete conversation history in subsequent API requests (exam wording). [Guide 5.1]
  • Keep it lean: trim big tool results to the fields that matter (for example 5 of 40 order fields), and keep key facts (amounts, dates, IDs) in a "case facts" block that never gets summarised away. [Guide 5.1]
  • Right: "Append the assistant turn and the tool results to messages, then call again."
  • Wrong: "Send only the latest user message; the API remembers the session."

Step 2. Branch on stop_reason

  • Checks: the stop_reason field of the response. Never the text.
  • Results: [stop-reasons]
    • tool_use → Step 3. Continue the loop. [Guide 1.1]
    • end_turn → done. Return the answer. [Guide 1.1]
    • max_tokens → the reply was cut off. If it stopped inside a tool call, the tool_use block is incomplete: don't run it. Retry with a higher max_tokens.
    • stop_sequence → one of your stop strings was hit; handle as your design says.
    • pause_turn → a server-tool loop hit its limit. Send the assistant content back to continue.
    • refusal → Claude declined. Read stop_details; today's docs suggest a fallback model. Don't loop blindly.
    • model_context_window_exceeded → treat the reply as truncated.
  • Right: "Continue while stop_reason == "tool_use"; stop on "end_turn"."
  • Wrong (exam wording for the anti-patterns, [Guide 1.1]): parsing natural language signals to determine loop termination, setting arbitrary iteration caps as the primary stopping mechanism, or checking for assistant text content as a completion indicator. A cap as a backstop for runaway loops is fine; as the main stop it is wrong.

Step 3. Run every tool block and send results back

  • Checks: every tool_use block in the response, by id.
  • Results:
    • Each one gets a tool_result with the matching tool_use_id. [handle-tools]
    • All tool_result blocks go first in the next user message; any text goes after. Text first is a 400. [handle-tools]
    • Parallel calls: every result goes back in one single user message, with no text before the results. [parallel]

Step 1. Find the session

  • Checks: which earlier conversation do you want?
  • Results (exact, [cli]):
    • The most recent one in this folder → --continue (-c). Interactive --continue skips sessions made with claude -p or the Agent SDK; claude -p --continue includes -p, SDK and /loop sessions, which matters for CI jobs that pick up where they left off. [cli]

    • No → Step 3.

    • Stale → start a new session with a structured summary. starting a new session with a structured summary is more reliable than resuming with stale tool results.
  • How code knows what changed: compare file hashes, timestamps or git diff since the last session (practice, not doc). Re-read only those files.

Step 4. Make the work survive

    • Key findings → a scratchpad file the agent writes and re-reads. [Guide 5.4]
    • Crash recovery → each agent exports state to a known place; the coordinator loads a manifest on resume and puts it into agent prompts. [Guide 5.4]
    • Long chats → keep numbers, dates and promises in a facts block; summaries blur them. [Guide 5.1]

Step 1. Is it blocking?

  • Checks: is a merge or a developer waiting on this?
  • Results:
    • Yes (pre-merge check) → synchronous: headless Claude Code or the Messages API. [Guide 4.5]
    • No (nightly test generation, weekly audit) → Message Batches API for 50% savings. [Guide 4.5]
  • Wrong: "Use Batch for the pre-merge review to cut cost." Batch has no latency promise.

Step 2. Run headless with machine-readable output

  • Checks: will the job hang waiting for input, and can the pipeline parse the result?
  • Results (exact, [cli] and [Guide 3.6]):
    • -p / --print → non-interactive. Without it, CI can hang waiting for input.
    • --output-format json → parseable output (text, json, stream-json).
    • --json-schema '<schema>' → validated JSON matching your schema (print mode only). With --output-format json, the answer sits in the structured_output field of the JSON reply, next to metadata, so the pipeline reads .structured_output. [headless]
    • Limits: --max-turns N (print mode only; exits with an error at the limit; no limit by default, so a CI job has no cap unless you set one), --max-budget-usd, --permission-mode. [cli]
    • --allowedTools pre-approves tools so they run without a prompt; for Glob and Grep, which are off by default on macOS, Linux and WSL, naming them also turns them back on. --tools is what restricts the set. [cli] [tools]
    • The API key comes from the CI secret store as an environment variable.
    • GitHub Actions has an official Claude Code integration (setup details not re-checked today).
  • What changed since: today's docs say "In CI or other scripted environments, add --bare", and it will become the default for -p later. --bare skips hooks, skills, custom commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md, so with it you pass standards in explicitly (for example --append-system-prompt-file). Without --bare, a -p run uses the project's .claude/settings.json hooks and .mcp.json servers even in a folder you've never trusted, which is unsafe for untrusted code. [headless] [cli] On the exam: pick -p with CLAUDE.md in the repo as the way CI gets project context.

  • Wrong: "Run claude interactively in the CI container", or "parse the free-text reply with a regex".

  • Checks: where does CI Claude learn the team's standards?
  • Results: CLAUDE.md in the repo holds testing standards, fixture conventions and review criteria.   • For test generation: put existing test files in context so it doesn't suggest tests that already exist. [Guide 3.6]

Step 4. Pick what to read

  • Checks: what changed?
  • Results: start from git diff. Read the changed files, Grep for callers and tests of changed functions. Don't load the whole repo (practice, not doc; see Flow 8).
  • Big PR: split into per-file passes for local issues plus a separate cross-file integration pass. This avoids attention dilution (exam wording). [Guide 4.6] [Guide 1.6]

Step 5. New commit on the same PR

  • Checks: have we reviewed this PR before?
  • Results: yes → include the earlier findings and tell Claude to report only new or still-unaddressed issues, so it doesn't post duplicates. [Guide 3.6]
  • Wrong: "Re-run the full review from scratch and post everything again."

Step 6. Review with an independent instance

  • Checks: is the reviewer the same session that wrote the code?
  • Results: it must not be. A model retains reasoning context from generation, making it less likely to question its own decisions (exam wording). Use a second, independent instance. That beats "review yourself carefully" and beats extended thinking. [Guide 4.6] [Guide 3.6]

Step 7. Write criteria that cut false positives

  • Checks: are developers ignoring the comments?
  • Results (exam wording, [Guide 4.1]):
    • Use explicit criteria: what to report (bugs, security) and what to skip (minor style, local patterns).
    • "Be conservative" or "only report high-confidence findings" does not improve precision.
    • Temporarily turn off a high-false-positive category while you fix its prompt, to win back trust.
    • Define each severity with concrete code examples.
    • Few-shot examples of acceptable code vs real issues help Claude generalise. [Guide 4.2]

Step 8. Gate on facts, output, and failures

  • Checks: did tests actually pass, and is the output valid?
  • Results:
    • Pass/fail comes from real test exit codes, not from Claude saying "tests pass" (practice, not doc).
    • Schema-valid findings (file, line, severity, message) → post as inline PR comments. [Guide 3.6]
    • Invalid → retry once with the error, then mark "needs a person". Never auto-approve.
    • Background, not tested: 429, 500, 529 → retry with backoff (the SDK retries twice by default, honouring retry-after). A 429 with no retry-after may be a spend cap; backoff won't fix it, so fail and alert. [errors]
    • Max turns hit → the run exits with an error; fail the job visibly. [cli]

Step 1. Read the map first

  • Checks: does the repo already explain itself?
  • Results: read CLAUDE.md, the README and the top-level folder list before searching (practice, not doc).

Step 2. Glob or Grep?

  • Checks: do you know a file name pattern, or some text inside files?
  • Results (exam wording, [Guide 2.5]):
    • Name or extension → Glob, file path pattern matching, for example **/*.test.tsx.
    • Text inside files (function names, error messages, imports) → Grep, content search.
    • First see which files match, then look at content in the few that matter. The Grep tool's default mode is files_with_matches (file paths only); ask for content mode with a few lines of context after that. [tools]
  • What changed since: today Glob and Grep are absent by default on macOS, Linux and WSL (Claude searches through Bash instead). They come back when you name them in --tools or --allowedTools, or when Bash is removed. [tools] On the exam: pick Glob for names and Grep for content.
  • Right: "Grep for processRefund( to find every caller."
  • Wrong: "Glob for *refund*" when the question is who calls a function. Glob only sees names.

Step 3. Read selectively and build up

  • Checks: do you need the whole file?
  • Results: start with Grep to find entry points, then Read to follow imports and trace the flow, rather than reading all files upfront (exam wording). [Guide 2.5] For big files, read a line range.
  • Wrapper modules: first list every name the wrapper exports, then Grep for each name across the codebase. [Guide 2.5]

Step 4. Editing: Edit, or Read + Write?

  • Checks: is the text you want to change unique in the file?
  • Results: unique → Edit (targeted change by unique text match). Not unique, so Edit fails → Read the full file, then Write it back changed. [Guide 2.5]
  • What changed since: today's Edit tool has two more options: a longer old_string with enough surrounding text to be unique, or replace_all: true when you really want every match changed. [tools] On the exam: pick Read + Write when Edit can't find unique text.
  • Wrong: "Use Bash sed to force it" or "keep retrying Edit with the same text".

Step 5. Write things down

  • Checks: will today's findings survive a long session or a new one?
  • Results: keep a scratchpad file of entry points, key classes and open questions; re-read it for later questions. This fights Context degradation in extended sessions: models start giving inconsistent answers and referencing "typical patterns" rather than specific classes discovered earlier (exam wording). [Guide 5.4] Use /compact when discovery output piles up. [Guide 5.4]

Step 6. Split broad questions

  • Checks: will this question pull in lots of raw output?
  • Results: spawn a subagent per question ("find all test files", "trace refund flow dependencies"). Each returns a short summary; the main agent keeps the big picture. Summarise one phase before starting the next and put that summary into the new subagents' first prompt. [Guide 5.4] The Explore subagent isolates verbose discovery and returns summaries. [Guide 3.4]
  • Wrong: "Switch to a model with a bigger context window." That delays the problem; it doesn't fix it.

Step 7. Load the right conventions

  • Checks: do the rules apply everywhere, in one folder, or to one file type spread everywhere?
  • Results:
    • Everywhere → project CLAUDE.md. [Guide 3.1]
    • One file type across many folders (tests, Terraform) → .claude/rules/ file with YAML front matter paths: glob patterns, for example paths: ["terraform/**/*"] or **/*.test.tsx. Loads only when editing matching files. [Guide 3.3] [memory]
    • A task you run on demand → a skill in .claude/skills/ with SKILL.md. context: fork runs it in an isolated sub-agent; allowed-tools limits its tools (exam answer; today it only pre-approves and disallowed-tools blocks; see exam answer vs today); argument-hint prompts for missing arguments. [Guide 3.2] [skills]
  • Wrong: "A CLAUDE.md in every test folder" for a test rule. Path rules handle spread-out files.

Step 8. Plan or just do it?

  • Checks: how big and how open is the change?
  • Results (exam wording, [Guide 3.4]):
    • Large-scale, many valid approaches, architecture choices, multi-file (for example a migration touching 45+ files) → plan mode first, then execute the plan.
    • Simple, clear scope (one-file bug fix with a clear stack trace) → direct execution.
  • Open-ended tasks ("add tests to a legacy codebase") → map structure, find high-impact areas, make a prioritised plan that changes as you learn. [Guide 1.6]
