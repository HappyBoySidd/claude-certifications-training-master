5.1 Preserving context in long interactions

Plain ↔ technical · context window / compaction

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Keep a small working brief without losing the exact facts that decide the next action. A summary is useful only if critical uncertainty survives.

Does not establish: A compacted conversation is not a refreshed policy or authorization record, and shortening text must not erase an unresolved payment.

In technical terms

context window compaction durable state decision-critical facts source pointers

Inspect the technical example

Application checkpoint/brief pseudocode — fields are authored business state

durable_case = {
  case_id:"C-41", requested_amount_minor:18720,
  approval:{amount_minor:6000, policy:"v3"},
  current_policy:"v4", operation:{id:"OP-6", status:"unknown"},
  sources:["booking:B-52", "approval:A-6"]
}
brief = select_next_decision_facts(durable_case)

Read it as: The brief retains exact amounts, approval scope and unknown effects while source pointers permit inspection. Compaction manages model context; the application owns durable business facts.

Official mechanism reference

Lesson: L05 section 5.1 · Objective: 5.1

Exam wording: Task Statement 5.1: Manage conversation context to preserve critical information across long interactions

Core idea

Claude's API has no memory. Every call starts from zero. The only thing Claude knows is what you send in that call. So your app must send the whole conversation every time, and it must protect the exact facts (amounts, dates, order numbers) from getting blurred when the conversation gets long.

How it works under the hood

  • Stateless. Doc wording: "The Messages API is stateless, which means that you always send the full conversational history to the API" [messages]. Your code keeps the messages list and appends each assistant reply and each user turn (including tool_result blocks) before the next call. Earlier turns can even be synthetic assistant messages you wrote [messages].
  • Exam knowledge wording: "The importance of passing complete conversation history in subsequent API requests to maintain conversational coherence" [guide, TS 5.1].
  • Summaries lose numbers. Exam knowledge: "Progressive summarization risks: condensing numerical values, percentages, dates, and customer-stated expectations into vague summaries" [Guide]. "$212.40 refund on order ORD-88123 promised by Friday" becomes "customer wants a refund".
  • Fix: a case-facts block. Exam skill: extract "transactional facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block included in each prompt, outside summarized history" [Guide]. The summary may shrink. The facts block never does.
  • Lost in the middle. Exam knowledge: models "reliably process information at the beginning and end of long inputs but may omit findings from middle sections" [Guide]. Fix: put a key-findings summary at the start and use clear section headers [Guide].
  • Trim tool output. Exam knowledge: tool results consume tokens "disproportionately to their relevance (e.g., 40+ fields per order lookup when only 5 are relevant)" [Guide]. Keep only the fields you need before appending.
  • Upstream agents return structure. When the downstream agent has a small budget, have upstream agents return "key facts, citations, relevance scores" instead of "verbose content and reasoning chains" [Guide].
case_facts = {"customer_id": "C-4471", "order": "ORD-88123", "refund_amount": 212.40,
              "promised_by": "2026-10-09", "status": "approved_pending_payout"}
system = BASE_PROMPT + "\n<case_facts>\n" + json.dumps(case_facts) + "\n</case_facts>"
resp = client.messages.create(model=M, system=system,
                              messages=summarized_history + recent_turns,   # full history, every call
                              max_tokens=1024, tools=TOOLS)

Look-alikes

  1. "Claude remembers the session, so only send the new message." No. The API is stateless. (Claude Code and the Agent SDK store sessions for you, but they still send history to the model on every call; the plain Messages API does not store anything.)
  2. "Summarize the whole history every 10 turns to save tokens." Fine for chatter, but on its own it blurs the exact numbers. Pair it with a case-facts block.
  3. "Use a model with a bigger context window." Doesn't fix lost-in-the-middle or blurred summaries.
  4. "Keep every field from every lookup in case it's useful later." Fills context with noise.

Worked example (Scenario: customer support resolution agent)

A 45-minute chat covers two orders. By turn 30, the agent says the refund is "about $200" and mixes up which order was damaged. Fix: keep a case_facts block per issue (order ID, amount, status, promise date) in the system prompt on every call; trim lookup_order results to the 5 return-relevant fields; keep the summarized history for the chatter.

Exam reflex

The API remembers nothing: send the full history, pin exact facts in a case-facts block, trim tool output.

5.3 Error propagation across multi-agent systems

Plain ↔ technical · error propagation / partial success

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A failed specialist must remain visibly failed when its result reaches the coordinator. Preserve successful evidence without claiming the whole job is complete.

Does not establish: A schema-valid combined object does not prove every required investigation returned; majority success does not erase a mandatory missing dimension.

In technical terms

error propagation partial success expected versus observed returns failure classification coverage reconciliation

Inspect the technical example

Application worker-return contract pseudocode — not Agent SDK reserved fields

expected = ["connectivity", "ergonomics"]
returns = [
  {worker:"ergonomics", status:"supported", claims:[{source:"S2", locator:"p4"}]},
  {worker:"connectivity", status:"failed", cause:"timeout", claims:[]}
]
coverage = reconcile(expected, returns)
# Retry eligible missing work within budget, or finalize explicitly partial.

Read it as: An empty successful search and a failed search are different observations. The coordinator checks assigned coverage and keeps evidence links rather than replacing the failure with guessed findings.

Official mechanism reference

Lesson: L05 section 5.3 · Objective: 5.3

Exam wording: Task Statement 5.3: Implement error propagation strategies across multi-agent systems

Core idea

When a helper agent hits a problem, it should fix what it can by itself, and pass up the rest with details: what failed, what it tried, what it already got, and what else could work. Never hide a failure. Never kill the whole job over one failure.

How it works under the hood

  • Exam knowledge wording: "Structured error context (failure type, attempted query, partial results, alternative approaches)" enables "intelligent coordinator recovery decisions" [guide, TS 5.3].
  • The two anti-patterns, exam wording: "silently suppressing errors (returning empty results as success) or terminating entire workflows on single failures" [Guide].
  • "Generic error statuses ("search unavailable") hide valuable context from the coordinator" [Guide].
  • Access failure vs valid empty result: same rule as 2.2 (see deep practice 2).
  • Local recovery first: subagents handle transient failures themselves and "only propagate errors they cannot resolve, including what was attempted and partial results" [Guide].
  • Coverage notes in the output. Exam skill: synthesis output "with coverage annotations indicating which findings are well-supported versus which topic areas have gaps due to unavailable sources" [Guide].
  • Anthropic's research system: letting "the agent know when a tool is failing and letting it adapt works surprisingly well", and they built it to "resume from where the agent was when the errors occurred" [research-system].

A good subagent error report (practice, not doc):

{"status": "partial", "failure_type": "timeout", "attempted": "search: 'EU AI Act enforcement 2026' on news API (3 tries, backoff)",
 "partial_results": [{"claim": "...", "source_url": "..."}],
 "alternatives": ["try the legal-database source", "narrow to 2026-Q3"],
 "coverage_gap": "No enforcement data after July 2026"}

Look-alikes

  1. Subagent returns [] as success after a timeout. Coordinator thinks "no news exists". Silent suppression.
  2. Coordinator aborts the whole report when one of five searches fails. Over-reaction; keep the other four and annotate the gap.
  3. Subagent returns "search unavailable". Too generic; no retry decision possible.
  4. Subagent passes every transient error up to the coordinator. It should retry those locally first.

Worked example (Scenario: multi-agent research system)

Five search subagents run; one gets rate-limited. Good design: it retries with backoff, still fails, then returns failure_type, the query it tried, its two results so far, and an alternative source. The coordinator re-delegates to the alternative source. The final report says "Regulatory section: limited coverage, primary source unavailable".

Exam reflex

Recover locally, propagate the rest with type, attempt, partial results and alternatives; never hide it, never abort everything.

5.4 Context in large codebase exploration

Plain ↔ technical · targeted search / dependency trace

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Explore a large repository by following evidence from the symptom into its actual dependencies. Keep the paths and findings so you do not reread everything.

Does not establish: Reading the entire repository is not the same as understanding the relevant path; a stale note is not current implementation evidence.

In technical terms

targeted search dependency trace evidence ledger context budget progressive expansion

Inspect the technical example

Claude Code exploration workflow pseudocode — no fabricated tool-call signatures

Grep: locate deposit normalization and balance_known
Read: importer.py, report.py and the relevant fixtures
ledger: path + symbol + observed behavior + next dependency
Expand: read a shared helper only when the current trace reaches it
Check: verify against current files before proposing the patch

Read it as: The ledger preserves where each observation came from. A newly demonstrated shared helper justifies expanding scope; an old summary cannot replace checking its current code.

Official mechanism reference

Lesson: L05 section 5.4 · Objective: 5.4

Exam wording: Task Statement 5.4: Manage context effectively in large codebase exploration

Core idea

Long exploration fills the context with search output. Claude starts to forget the specific things it found and talks about "typical patterns" instead. Three fixes: send noisy searches to subagents that return short summaries; write key findings to a scratchpad file that survives; and /compact when context fills.

How it works under the hood

  • The symptom, exam wording: "models start giving inconsistent answers and referencing "typical patterns" rather than specific classes discovered earlier" [guide, TS 5.4].
  • Subagents isolate noise. Doc: intermediate tool calls and results "stay inside the subagent; only its final message returns to the parent" [sdk-subagents]. Anthropic: a subagent may use "tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)" [context-eng]. Exam skill example tasks: "find all test files," "trace refund flow dependencies" [Guide].
  • Scratchpad files. Exam knowledge: "The role of scratchpad files for persisting key findings across context boundaries" [Guide]. Anthropic calls this structured note-taking, like "your custom agent maintaining a NOTES.md file" [context-eng].
  • What survives /compact. Doc: "Project-root CLAUDE.md survives compaction: after /compact, Claude re-reads it from disk and re-injects it into the session." An instruction given "only in conversation" can disappear [cc-memory]. Compaction summarizes the conversation, so details only in chat may be lost. A scratchpad file is on disk, so Claude can read it again after /compact or in a new session. (Survival of a scratchpad file is from it being on disk; Claude must be told to re-read it: practice, consistent with [cc-memory] and [context-eng].)
  • /compact, exam skill: "Using /compact to reduce context usage during extended exploration sessions when context fills with verbose discovery output" [Guide].
  • Phase summaries. Summarize one phase's findings "before spawning sub-agents for the next phase, injecting summaries into initial context" [Guide].
  • Crash recovery with manifests. Exam knowledge: "each agent exports state to a known location, and the coordinator loads a manifest on resume" [Guide]. Example: each agent writes state/<agent>.json; the coordinator keeps state/manifest.json listing done and pending tasks; on restart it loads the manifest and injects each agent's state into its prompt.
  • Search order that keeps context small: Glob, then Grep file list, then narrowed Grep content, then Read with offset/limit [cc-tools]. Details in deep practice 2, 2.5.

Look-alikes

  1. "Use a bigger context window." Delays the problem; doesn't remove noise.
  2. "Restart the session when answers get vague." Loses everything not written down. Write a scratchpad first, or delegate the noisy part.
  3. "Do every search in the main agent so it sees everything." That's what floods it.
  4. "Fork the session to explore." A fork carries the full history; for isolating noisy output you want a fresh subagent with a short summary back.
  5. "Rely on /compact alone." It helps, but a summary can drop specific class names; pair it with a scratchpad.

Worked example (Scenario: developer productivity with Claude)

First day of learning a 2,000-file monorepo. After two hours Claude says "refunds are probably handled by a typical service layer", though it found RefundOrchestrator earlier. Fix: (1) Claude writes notes/exploration.md with entry points, key classes (RefundOrchestrator, LedgerClient) and open questions, and re-reads it before each new question; (2) "trace refund flow dependencies" goes to a subagent that returns a 1-page summary; (3) /compact when the context fills with search output.

Exam reflex

Noisy searches go to subagents, findings go in a scratchpad file, /compact when full; never "bigger window".

5.6 Provenance and uncertainty in multi-source synthesis

Plain ↔ technical · provenance / claim-to-source mapping

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Keep each claim attached to its source and time. A neat combined answer must not erase disagreement or pretend two systems have identical authority.

Does not establish: A unified query interface does not guarantee consistent records, and a citation does not establish that the cited source governs this field.

In technical terms

provenance claim-to-source mapping citation source locator timestamp conflict

Inspect the technical example

Application synthesis record pseudocode — not Anthropic citation response fields

claims = [
  {field:"termination_date", value:"date_A", source:"contract:S1", locator:"section9", as_of:"t1"},
  {field:"termination_date", value:"date_B", source:"system:S2", locator:"row17", as_of:"t2"}
]
answer = {claims:claims, conflict:"unresolved", governing_authority:"not established"}

Read it as: The source and locator travel with each value. Native citation features have their own documented response shapes; this application record is a separate way to preserve provenance through workers and joins.

Official mechanism reference

Lesson: L05 section 5.6 · Objective: 5.6

Exam wording: Task Statement 5.6: Preserve information provenance and handle uncertainty in multi-source synthesis

Core idea

Every claim should carry its source, all the way to the final report. When sources disagree, show both with their sources. Don't quietly pick one. And record dates, because "different numbers" might just be "different years".

How it works under the hood

Exam wording [guide, TS 5.6]:

  • Knowledge: "source attribution is lost during summarization steps when findings are compressed without preserving claim-source mappings".
  • Skill: subagents output "structured claim-source mappings (source URLs, document names, relevant excerpts) that downstream agents preserve through synthesis".
  • Conflicts: "annotating conflicts with source attribution rather than arbitrarily selecting one value". Document analysis completes "with conflicting values included and explicitly annotated, letting the coordinator decide how to reconcile".
  • Dates: require "publication or data collection dates in structured outputs to enable correct temporal interpretation".
  • Report structure: "explicit sections distinguishing well-established findings from contested ones".
  • Format by type: "financial data as tables, news as prose, technical findings as structured lists".

Anthropic's research system adds a final citation pass (a CitationAgent) so "all claims are properly attributed to their sources" [research-system]. This final pass is an extra check on top of structured claim-source mappings, not a replacement for them; on the exam, pick the mappings.

{"claim": "Global AI-music market size", "values": [
  {"value": "$3.9B", "source": "Report A", "url": "...", "published": "2025-02", "method": "survey"},
  {"value": "$6.2B", "source": "Report B", "url": "...", "published": "2026-06", "method": "revenue model"}],
 "status": "contested", "note": "Different years and methods; not necessarily a contradiction."}

Look-alikes

  1. "Pick the most recent / most credible number and drop the other." Arbitrary selection; the exam wants both, annotated.
  2. "Average the two figures." Invents a number no source said.
  3. "Summarize findings into clean prose first, add citations at the end." Compression already lost the claim-source links.
  4. "Render everything as bullet points for consistency." The guide wants format by content type.

Worked example (Scenario: multi-agent research system)

Two credible sources give different market sizes. The analysis subagent includes both with source, date and method, and marks the item contested. The coordinator sees one is 2025 data and one is 2026 data, so the report shows a growth trend rather than a contradiction, in a table, with both citations.

Exam reflex

Claims carry sources and dates end to end; conflicts are shown with attribution, never silently resolved.

1.7 Session resumption: what a resumed session still knows

Plain ↔ technical · session_id / resume

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A saved conversation helps you continue an investigation. It does not refresh an old policy or give permission for a different payment.

Does not establish: Persisted session history is not a filesystem snapshot, current authorization or proof that an unknown transaction failed.

In technical terms

session_id resume fork conversation history freshness check

Inspect the technical example

Application resume policy pseudocode — not an Agent SDK call signature

load_session(saved_session_id)
load_exact_operation_state("OP-6")
refresh(current_policy, decision_critical_evidence)
revalidate(approval_amount, approval_scope, current_request)
# Resume the investigation; do not infer payment completion from history.

Read it as: Session restoration and business-state revalidation are different jobs. Forking branches a conversation; it does not roll back external payments or files.

Official mechanism reference

Lesson: L01 section 1.7 · Objective: 1.7

Exam wording: Task Statement 1.7: Manage session state, resumption, and forking

Flags and SDK options are in deep practice 1, 1.7. This part is about what a resumed session still knows and when not to resume.

Core idea

Resuming brings back the old conversation, including old tool results. If the code changed since then, those old results are wrong, and Claude doesn't know it. So either tell it exactly what changed, or start a new session with a clean summary.

How it works under the hood

  • --continue / -c: the most recent conversation in this directory. --resume / -r: a specific session by ID or name. --fork-session: a new session ID with the old history [cli]. SDK: continue, resume with a session_id, and fork_session / forkSession [sdk-sessions].
  • In CI: plain claude --continue skips sessions made with claude -p, but "claude -p --continue includes -p, SDK, and /loop sessions" [cli].
  • Exam knowledge wording [guide, TS 1.7]:
    • "The importance of informing the agent about changes to previously analyzed files when resuming sessions after code modifications"
    • "Why starting a new session with a structured summary is more reliable than resuming with stale tool results"
  • Exam skill wording: "Choosing between session resumption (when prior context is mostly valid) and starting fresh with injected summaries (when prior tool results are stale)" and "Informing a resumed session about specific file changes for targeted re-analysis rather than requiring full re-exploration" [Guide].

The decision:

What changed since the last session?Move
Nothing, or very little--resume <name> and continue.
A few known files--resume <name>, then say: "auth/session.py and auth/tokens.py changed (commit abc123). Re-read only those and update your findings."
A lot (big refactor, branch switch)New session. Inject a structured summary of the earlier findings. Let Claude re-read what it needs.
Want to try two directionsFork (see deep practice 1).

Practice pattern (practice, not doc): find what changed with git diff --name-only <last-reviewed-commit> or file hashes, and list those files in the resume message.

Look-alikes

  1. "Resume and ask Claude to re-check everything." Full re-exploration wastes time and context; the exam wants targeted re-analysis of named files.
  2. "Resume; Claude will notice the files changed." It won't. Its old Read results look current to it.
  3. "--continue to get yesterday's auth-audit session." Only if it's the most recent one in this directory. Use --resume auth-audit.
  4. "Always start fresh to be safe." Throws away valid context when little changed.

Worked example (Scenario: Claude Code for continuous integration)

A PR review session found 6 issues. The developer pushes a new commit touching 2 files. Right move: resume the review session and tell it which 2 files changed, so it re-checks just those and doesn't re-post the other comments. Twist: the developer rebased onto a main branch that moved 300 files. Now prior results are stale: start a fresh session with a summary of the 6 earlier findings.

Exam reflex

Mostly valid: resume and name the changed files; mostly stale: fresh session plus summary.
