1. First name the guarantee

Plain ↔ technical · output_config.format / json_schema

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Choose the mechanism for the boundary you need: a machine-readable final response or valid arguments for a requested tool. Then check whether the values are actually supported.

Does not establish: Valid JSON and schema-compliant integers do not establish correct units, source truth, permissions or completed business effects.

In technical terms

output_config.format json_schema strict:true input_schema schema conformance

Inspect the technical example

Actual request-field fragment for final structured JSON; model and remaining request fields omitted

{"output_config":{"format":{"type":"json_schema","schema":{"type":"object","properties":{"total_minor":{"type":"integer"},"currency":{"type":"string","enum":["USD"]}},"required":["total_minor","currency"],"additionalProperties":false}}}}

For supported strict tool arguments, strict:true belongs on the tool definition;
it is not the same field as output_config.format.

Read it as: This fragment constrains final JSON shape. Strict tool use constrains a different boundary. Verify current model/schema support and handle refusals or incomplete responses before consuming results.

Official mechanism reference

A legal intake service needs machine-readable fields. Plain meaning: asking for a shape, forcing an operation and proving facts are different jobs.

RequirementTechnical mechanism to considerWhat it does not establish
Final response must follow a supported JSON schemaCurrent API output_config.formatCorrect source facts or business completion
Generated tool arguments must follow the supported input schemaCurrent tool definition strict: trueThat a tool is selected, authorized or executed
A tool must be requestedAppropriate tool_choiceCorrect values, permitted action or ordering of dependencies
MCP server returns a declared result shapeProtocol outputSchema and structuredContent, with client validationConstrained generation of the model's final answer
CLI review needs a machine-readable resultPrint-mode JSON output and result schemaTest execution, permission enforcement or correct findings

Today, not a replacement exam key: supported structured-output features constrain shape. Handle refusal and truncation explicitly; don't parse them as ordinary success. Current documentation also describes enum-casing limitations. These qualifications matter even when a request succeeds. Avoid a universal ladder that treats prefill as supported on every model or tool selection as stricter factual validation.

Read API structured outputs, strict tool inputs and MCP tool results. Repair 4.3.

2. Separate a new category, ambiguity and absence

Plain ↔ technical · consumer validation / semantic validation

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A receiver should reject the exact bad field, allow a limited evidence-based correction, and preserve unresolved cases rather than looping forever.

Does not establish: Retrying the same prompt or taking model consensus is not semantic validation. Never normalize unknown facts into fabricated values.

In technical terms

consumer validation semantic validation bounded retry field-level feedback quarantine

Inspect the technical example

Application validation/repair pseudocode — not reserved API fields

proposal = {total_minor:84.5, currency:"USD"}
errors = ["total_minor must be integer cents", "purchase_order key missing"]
feedback = {source:"EL-8 USD84.50; PO absent", errors:errors}
for attempt in bounded_repair_budget:
    revised = request_source_based_correction(feedback)
    if shape_valid(revised) and agrees_with_source(revised): return accepted(revised)
route_unresolved_to_review()

Read it as: The feedback includes both the defect and source evidence. A whole number such as 845 can still fail agreement with USD84.50. Retry conditions and maximum attempts are application choices.

Official mechanism reference

An invoice says “carbon offset,” but the approved categories are equipment and services. This is different from illegible category text or a missing category. Design distinct representable states: a permitted other category plus source detail for a clear new value, an explicit review/uncertainty state for ambiguous evidence, and optional/nullable representation for absence when the contract allows it. These labels are application design choices, not magic schema keywords. Keep the original text as evidence. Do not silently force the closest category.

A field can be required yet nullable; optional means the key may be omitted. Choose according to the downstream contract. A required non-null field does not create missing evidence: provide a review/error path rather than invent a value. A confidence number does not resolve a contradictory source. Repair validation 4.4 and human review 5.5.

3. Control invocation and dependencies separately

Plain ↔ technical · execution-time authorization / prerequisite gate

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

The program that can change a record must check the prerequisites immediately before the change. If blocked, pass the next owner a complete case.

Does not establish: Selecting the right tool or passing JSON validation does not authorize that action.

In technical terms

execution-time authorization prerequisite gate scoped approval human handoff

Inspect the technical example

Application control-flow pseudocode — fictional policy, not a Claude API feature

if trusted_session.account != order.owner:
    return blocked("ownership_mismatch")
if proposed_cents > 18000 and not scoped_staff_approval:
    return pending_review(case, evidence, proposed_cents, operation_state)
submit_credit(permitted_exact_action)

Read it as: The trusted login comes from the application, not the proposed tool arguments. The review packet says whether money was submitted or is only proposed.

Official mechanism reference

For a supported tool-use request, auto permits a text response; any requests some tool; selecting a named tool requests that tool. Neither array position nor a prompt reminder creates an executable dependency gate. Model/feature compatibility still applies.

Trace: request account lookup → runtime receives its result → validate customer/account binding → enable the dependent operation only when prerequisites pass. A named prerequisite call alone is insufficient: its result can be denied, missing or invalid. Independent reads may run together; a dependent action must wait. Repair tool choice 2.3 and enforcement 1.4; consult tool definitions and choice.

4. Pick the right configuration layer

Plain ↔ technical · PreToolUse / PostToolUse

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A before-action hook can stop a prohibited call. An after-action hook can inspect an observed result, but cannot undo a completed side effect.

Does not establish: A PostToolUse check cannot retroactively prevent an effect that has already occurred; hook control is not a replacement for business authorization.

In technical terms

PreToolUse PostToolUse hookSpecificOutput permissionDecision

Inspect the technical example

Actual PreToolUse hook JSON decision shape; illustrative denial reason

{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"This action is outside the permitted task scope."}}

Read it as: This is hook output for the named lifecycle event, not a message sent as tool_result. Hook behavior depends on the event; verify the configured handler actually runs.

Official mechanism reference

NeedCandidate layerClose alternative that misses the need
Shared review conventionsProject CLAUDE.mdA personal file does not distribute team guidance
Conventions for matching pathsRules with paths globsLoading every rule everywhere adds irrelevant context
Reusable task instructionsSkillA skill description is not authorization
Pre-execution interceptionAppropriate pre-tool hookPost-processing cannot prevent an action already taken
Post-result normalizationAppropriate post-tool hookNatural-language guidance alone does not implement a transformation
Tool access policySettings permissions and applicable policyCLAUDE.md is not an enforceable access rule

Check effective precedence and supported behavior. An allow rule, mode, sandbox and downstream service permission are distinct boundaries. Do not assume one control covers all of them. Read permissions, settings scope and hook contracts. Repair 3.1, 3.3 and 1.5.

Skill fields today: context: fork changes execution context; argument-hint helps describe expected arguments; allowed-tools affects permission prompting for the skill. Do not interpret it as a universal deny-all policy. CLI --tools controls built-in tool availability; it does not control MCP tools. Configure MCP capabilities and their applicable permission rules separately. --allowedTools addresses permission prompting, a different concern. Check skill frontmatter and the CLI reference. Repair 3.2.

5. Configure a review without confusing its three needs

Plain ↔ technical · claude -p / --output-format json

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A CI job must finish or fail visibly without waiting for a person at a terminal. Keep review authority separate from posting, approval and merge authority.

Does not establish: A valid empty findings list is not proof of safe code, and a reviewer has no implicit authority to publish comments or merge.

In technical terms

claude -p --output-format json headless execution exit status result envelope bounded permissions

Inspect the technical example

Actual CLI flags with a fictional supplied review packet; illustrative shell invocation, not a complete CI deployment

claude -p "Review the supplied change against its contract" --output-format json < review-packet.txt > review-result.json

Consumer checks, in order:
1. Process completed successfully.
2. Expected result envelope is present and reports an acceptable run outcome.
3. Review payload parses and passes its contract.
4. Findings have independently checked code evidence.

Read it as: The command runs noninteractively and requests JSON output. The application must still check process and envelope status before interpreting a payload. Configure bounded permissions and credentials separately.

Official mechanism reference

A marketing-code review needs standards, permitted capabilities and machine-readable findings. Supply all three explicitly. Standards describe what a finding is; permission/tool configuration controls execution; output settings control the result envelope. One vague “review carefully” instruction meets none of these precisely.

Current CLI reference: -p runs noninteractively; --max-turns bounds agentic turns; --max-budget-usd limits estimated API spend in print mode and can overshoot. The budget is not an exact billing ceiling. --output-format json and --json-schema address output. Pin a supported CLI version, inspect its documented envelope and process status, and validate the extracted payload. Do not confuse output volume, permitted tools, turn count and budget. No permission-bypass flag is required by this lesson.

Read current CLI contracts; repair CI 3.6. Treat version-specific behavior as current-product guidance, not proof of exam weighting.

6. Improve the feedback, not just the number of retries

A generated test ignores a project's fixture conventions. Supply a minimal input, the observed output/failure and the expected behavior. Ask a focused question if the desired behavior is uncertain. Fix one independent issue at a time; group interacting failures when a shared cause requires joint reasoning. Then rerun the relevant check. There is no universal number of examples or retries.

Changed constraint: several failures share an incorrect parser contract. Repair the contract and its affected cases together rather than make unrelated cosmetic edits. Repair iterative refinement 3.5.

7. Choose a plan, then revise it when evidence changes

Plain ↔ technical · prompt chaining / routing

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

Choose the simplest work pattern that fits what you know. A fixed recipe suits known steps; an evolving investigation may need a coordinator to choose the next question.

Does not establish: A fixed workflow is not automatically an autonomous agent; adding agents does not fix a missing deterministic check.

In technical terms

prompt chaining routing parallelization orchestrator-workers evaluator-optimizer

Inspect the technical example

Architecture selection pseudocode — not an API configuration

if steps_known_and_dependent: use_fixed_chain()
elif independent_known_subtasks: use_parallel_checks()
elif next_tasks_depend_on_findings: use_bounded_orchestrator()
# Validate intermediate results and stop within an explicit budget.

Read it as: These are alternative designs, not mandatory layers to add together. Independent tasks can run together; a step needing another result must wait.

Official mechanism reference

For a small, well-understood edit, direct execution may be sufficient. For uncertain scope or consequential changes, inspect and plan; place required human approval before execution. Plan mode itself does not establish that an external approval workflow exists. Make the approval state enforceable where the application requires it.

During a repository investigation, a wrapper re-export reveals another dependency. Update the task graph and briefs; do not keep executing a now-incomplete fixed checklist. Parallelize independent investigations, sequence dependencies, and retain one integration owner. Repair planning 3.4 and adaptive decomposition 1.6.

8. Resume work from evidence-bearing state

Plain ↔ technical · session_id / resume

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

A saved conversation helps you continue an investigation. It does not refresh an old policy or give permission for a different payment.

Does not establish: Persisted session history is not a filesystem snapshot, current authorization or proof that an unknown transaction failed.

In technical terms

session_id resume fork conversation history freshness check

Inspect the technical example

Application resume policy pseudocode — not an Agent SDK call signature

load_session(saved_session_id)
load_exact_operation_state("OP-6")
refresh(current_policy, decision_critical_evidence)
revalidate(approval_amount, approval_scope, current_request)
# Resume the investigation; do not infer payment completion from history.

Read it as: Session restoration and business-state revalidation are different jobs. Forking branches a conversation; it does not roll back external payments or files.

Official mechanism reference

A legal-document pipeline stops after two of three branches finish. An application-owned manifest can record task IDs, source versions, completed outputs, unresolved work, artifact locations and authorization context. On resume, validate the manifest, recheck permissions/freshness and rerun only invalidated or missing work. A session identifier does not by itself restore every external side effect or specialist artifact. A manifest is a useful design pattern, not a mandatory Claude SDK file format.

Pass specialists the bounded question, relevant findings, source metadata and expected output. Neither a raw transcript dump nor a brief summary is always sufficient; preserve the exact details the next step needs. Repair sessions 1.7, context 5.1 and failures 5.3.

9. Verify MCP capability, not just connection

Plain ↔ technical · MCP / JSON-RPC

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

An MCP connection advertises capabilities. Your client still has to discover the tool, call it and bring back the result. A project-wide connection is different from one person’s local setup.

Does not establish: Configured server, discovered tool and completed tool execution are three different states. MCP metadata does not grant business authorization.

In technical terms

MCP JSON-RPC tools/list tools/call inputSchema .mcp.json project scope resources/read

Inspect the technical example

Actual MCP tools/call request shape; fictional tool/data, not a Messages tool_use block

{"jsonrpc":"2.0","id":17,"method":"tools/call","params":{"name":"lookup_order","arguments":{"order_id":"O4"}}}

Before this call: discover the available tool and its inputSchema through tools/list.
After it: inspect the actual MCP result/error before adapting it into your model conversation.

Resource content is a different protocol operation:
{"jsonrpc":"2.0","id":3,"method":"resources/read","params":{"uri":"manual://M4/R3"}}
Response excerpt:
{"jsonrpc":"2.0","id":3,"result":{"contents":[{"uri":"manual://M4/R3","mimeType":"text/plain","text":"Approved M4-R3 procedure..."}]}}

Read it as: MCP method and params belong to the client-server protocol. Anthropic Messages uses tool_use/input and tool_result instead; an adapter connects the two boundaries. tools/call invokes a capability; resources/read reads content at a URI. A catalog entry naming the URI is not its text and does not prove the model received it.

Official mechanism reference · Additional official reference · Additional official reference

A resource exposes URI-addressed context; a tool exposes an invocable capability, including read queries as well as writes. Do not equate resources with reads and tools with writes. The host chooses how resource context is incorporated. Compare MCP resources with MCP tools.

For Claude Code, check intended configuration scope, credential resolution, trust/approval and tool discovery. A connected server with no expected tool is not ready for the workflow. Use the current server-management/status interface and inspect exposed capabilities before a harmless authorized test. Keep actual secrets outside committed configuration. Transport and version affect setup; consult current MCP setup. Repair 2.4.

10. Explore narrowly and route review by evidence

Plain ↔ technical · Glob / Grep

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

First find the relevant files, then inspect their contents, and only then make a small change. Tool names describe different jobs, not interchangeable ways to guess what a repository contains.

Does not establish: A search hit is not the whole implementation, and a successful edit is not a successful test or deployed change.

In technical terms

Glob Grep Read Edit Write Bash targeted exploration

Inspect the technical example

Claude Code tool workflow pseudocode — semantic jobs, not tool-call JSON signatures

Glob: locate **/importer.py and related test paths
Grep: find deposit uses and report-formatting callers
Read: inspect current importer, formatter and relevant fixtures
Edit: change the specific proven boundary
Bash: run the relevant check and capture its actual outcome

Read it as: Glob locates paths; Grep locates matching content; Read supplies current code evidence. An Edit changes a known region; Write can replace file content and therefore needs a justified scope.

Official mechanism reference

Use Glob for candidate paths, Grep for entry points, then Read the relevant definitions and imports/re-exports. Inspect an edit mismatch before replacing a whole file; preserve unrelated changes. Trim excessive tool results at the source when possible, rather than summarize away the only evidence needed next. Retain durable business facts while reducing working context; a sliding window is a retention strategy, not a guarantee against information loss. Repair 2.5 and 5.4.

Route human review using consequences, contradictory fields, unfamiliar document types and calibrated evidence. Evaluate slices and sample apparently successful cases for silent errors. A model's confidence alone is not a validated probability. Escalation policy and authority remain application-specific: avoid universal sentiment-only or confidence-only rules. Repair 5.5.

Eight checks — commit before opening the explanation

Related technical reference · execution-time authorization / prerequisite gate

For choose two, name the two distinct requirements and justify each selection independently. A generally helpful option can still fail the stated requirement. Keep a paper tally of single-answer versus choose-two checks; these page-local checks do not change stored progress or establish readiness.

1. Choose TWO. A finance extractor must request a particular verification tool and constrain generated arguments. A: select the named tool through tool_choice; B: constrain final text through output_config.format; C: enable strict input-schema generation on the tool; D: declare outputSchema on the MCP server result.

A and C. Selection and generated argument shape are separate needs. B targets final text; D targets server results. Neither grants execution authority. Change: only final text needs a schema; choose its output mechanism instead. Repair sections 1 and 3.

2. Choose TWO. A legal repository needs shared review conventions and an enforced prohibition on a file-changing action. A: scope conventions through a personal memory file; B: distribute conventions through project guidance; C: normalize generated findings in a post-tool hook; D: enforce the action rule in effective permission policy.

B and D. Shared guidance distributes standards; policy constrains the prohibited action. A has the wrong audience; C acts after a result and does not prevent the action. Change: the convention applies only to matching files; consider path-scoped rules. Repair section 4.

3. One best. A clear invoice category is outside the approved enum, whose contract permits other plus source detail. A: extend the enum automatically on each observation; B: select other and retain the source detail; C: use null to represent every unfamiliar category; D: select the nearest permitted enum by semantic similarity.

B. It uses the explicit contract without losing the source. A changes a controlled vocabulary without approval; C confuses novelty with absence; D changes meaning. Change: evidence is absent or unreadable; use the corresponding absence or review state. Repair section 2.

4. Choose TWO. A CI review must run without interaction and bound agentic turns. A: request a JSON envelope and output schema; B: invoke the documented print execution mode; C: cap estimated API spend in the run budget; D: set the documented agentic-turn limit.

B and D. A controls representation; C addresses a different stopping constraint. Change: the requirement is estimated spend instead of turns; examine the budget control and overshoot caveat. Repair section 5.

5. One best. Two analysis artifacts survived an interruption, but access policy changed. A: resume worker sessions and reuse their prior authorization; B: reload the full transcript as the authoritative operation ledger; C: validate artifacts, reauthorize and recompute invalidated work; D: discard completed artifacts and rerun every branch from scratch.

C. A preserves stale authority; B confuses conversation with authoritative operation state; D discards potentially valid completed work. Change: a source version changed too; invalidate dependent outputs. Repair section 8.

6. One best. An MCP server connects, but its expected query tool is absent. A: treat transport status as proof of tool availability; B: revise the prompt with the expected tool description; C: increase the model context budget for the server; D: inspect discovery, configuration scope and approval.

D. Transport health, prompt context and capability discovery are distinct. B cannot expose an unavailable tool; C does not repair registration or approval. Change: the needed item is URI context rather than a tool; inspect resource support. Repair section 9.

7. One best. Generated tests repeatedly misuse a fixture whose required behavior is known. A: supply the failing example and expected fixture contract; B: load all repository files into the next model request; C: normalize test output with a post-execution hook only; D: rerun independent reviewers without changing their criteria.

A. It supplies targeted behavioral evidence. B adds broad context without isolating the error; C can change presentation without fixing assertions; D repeats the missing specification. Change: several failures share one parser defect; repair the interacting cause and retest affected cases together. Repair section 6.

8. One best. A wrapper reveals an unexamined dependency during a scoped review. A: retain the original fixed partition to preserve task order; B: revise subtasks and briefs within the approval boundary; C: fork the full conversation into each existing worker; D: persist the finding without updating task coverage.

B. A leaves a coverage gap; C does not assign ownership or revise dependencies; D records evidence but leaves the plan incomplete. Change: the finding requires an unapproved consequential action; obtain its required authorization while continuing independent permitted work. Repair section 7.
