Last reviewed: 2026-09-29

Time: 60 min · AI Fluency: Description · Practice: Lesson 1 practice set

Exam wording (exam guide v1.0, Domain 1):

  • Create effective prompts for business and technical tasks
  • Apply task decomposition techniques to structure complex requests
  • Iterate prompts to improve output quality
  • Adapt prompting strategies based on task type (analysis, research, drafting, brainstorming)

1. The big idea

Brief Claude the way you'd brief a brilliant new colleague who knows nothing about your situation. The test: if a coworker with no background couldn't do the job from your prompt, Claude can't either.

2. The parts of a professional prompt

PartWhat it doesExample
RoleSets the expertise and what "good" means"You are a skeptical financial controller…"
Goal / taskAn action verb plus the objectWrite, Analyze, Extract, Compare
Context / whyLets Claude make good choices you didn't spell out"This goes to the board, who have 8 minutes."
ConstraintsLength, must and must-not, allowed sources, toneSay what to do ("write in flowing prose"), not only what not to do
InputsDocuments and data, kept separate from instructions<documents>…</documents> tags
ExamplesShow the format and tone. 3–5 relevant, varied examples (Anthropic's prompting guide, Tier 1: "Include 3–5 examples for best results").Claude copies the details of your examples, so make them clean
ProcessSteps, when order matters"1. Quote the relevant passages. 2. Then analyze."
Output formatThe shape of the result"A table with columns X, Y, Z", or "an Artifact"
Uncertainty rulePermission to say "I don't know"Cuts down on made-up facts
Success criteriaHow you'll accept the workAn exam favorite

Long documents: put the document first and the question last, and ask Claude to quote first, then analyze.

Say it directly when you want action: "Change this", "create the Artifact", "search the web". "Can you suggest…" may only get suggestions.

3. Breaking work into steps (decomposition)

Split the job when there are several deliverables, mixed modes (research, then draft), a quality step that depends on an intermediate result, or a human checkpoint in the middle.

PatternUse when
Outline, then draftLong documents
Quote, then analyzeAnalysis grounded in a source
Rubric, then scoreClassification and review
Generate, then critiqueWriting where quality matters
Research, then synthesizeCurrent information
Plan on a stronger model, execute on a faster oneHeavy workflows

Exam tell: "Break it into steps with a review gate" beats "one longer prompt that does everything".

4. Iterating like a professional

  1. Run it against success criteria you wrote in advance.
  2. Name the failure: wrong format, missing section, invented fact, wrong tone, ignored constraint.
  3. Change one thing: add an example, move the question to the end, add "quote first", add permission to be uncertain, or split the task.
  4. Test again on the same input plus one edge case.

If three edits don't help, the problem probably isn't the prompt (see L07).

5. Adapting to the task type

TypeEmphasizeExtras
AnalysisRole, rubric, quote first"Separate facts, inferences and recommendations. What would change the conclusion?"
ResearchScope, sources, recency, citationsTurn on web search or Research, and allow "not enough sources" as an answer
DraftingAudience, tone, length, a sample of the voiceUse an Artifact and edit in place
BrainstormingQuantity, variety, don't judge yetAsk for N distinct options, then evaluate them in a second pass

6. Worked example

Weak: "Summarize these notes."

Strong: "You are a program manager writing for a busy VP. Goal: a one-page status they can read in 3 minutes. They care about schedule, budget and the decisions they need to make. <notes>…</notes>. 1) Pull out only the items that affect the timeline or budget, or that need a decision. 2) If the notes don't cover one of those, write 'Not in notes'; don't invent anything.

  1. Flag any ambiguous date or number. Use these headings: status (Red/Amber/Green and why),

progress, risks, decisions needed (with owner and date), open questions. Success means there are no facts that weren't in the notes."

6.1 Why the strong prompt wins

Map it back to the table in section 2:

  • "program manager writing for a busy VP" = role and audience (context)
  • "one page … in 3 minutes" = constraint
  • the numbered steps = process
  • "write 'Not in notes'; don't invent anything" = uncertainty rule
  • the list of headings = output format
  • "no facts that weren't in the notes" = success criteria

The weak prompt has none of these, so Claude has to guess all of them.

7. Traps

  • "Make the prompt longer or more polite" when the real issue is a missing success criterion.
  • Choosing zero-shot vs few-shot jargon over what actually fixes the problem. (Zero-shot = no examples; few-shot = with a few examples.) The exam asks what fixes the problem, not what it's called.
  • You don't need API system prompts (standing instructions a developer sets in code) or "prefill" (starting Claude's answer for it). Those are developer tools, and this exam has no code or API. On claude.ai, the Project instructions play the role of the system prompt (our explanation).

Try it (15 min, in Claude)

Take one prompt you really used this week and rewrite it using the table in section 2. Run both versions and write one line on what changed.
