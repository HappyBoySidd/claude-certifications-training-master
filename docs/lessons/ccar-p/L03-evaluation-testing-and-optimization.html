Time: 2 hours plus lab 05 · Practice: Lesson 3 practice set

Already covered in CCAR-F: per-field confidence, stratified sampling and "97% overall can hide a weak document type" are in CCAR-F L05. This lesson is about building the eval system, reading its results, and spending less without losing quality.

4.0 The big idea

If you can't measure it, you can't improve it. Decide what "good" means before you build, rerun the same test set every time anything changes, and fix the layer that actually broke instead of guessing.

4.1 Metrics: decide them before you build

Write the marking scheme before the exam: decide what a good result looks like before you write a single prompt.

MetricExample measures
Accuracy and qualityExact match, F1 on extracted fields, rubric score, groundedness (claims backed by a source)
LatencyTime to first token, total time, p95 against the SLA
CostTokens and dollars per request or per resolved case, cache hit rate
SafetyHarmful-output rate, correct refusals, over-refusals
SecurityPrompt-injection resistance, data leaks, unauthorized tool calls
  • Make success criteria specific and measurable, and judge on several dimensions at once (define success criteria).
  • Break results down by case type, language, customer group. One average hides the failures.

4.2 Eval datasets and mixed methods

  • Build the set from real traffic, and add edge cases, adversarial inputs and past incidents. Label the expected answer, or the expected properties, for each case.
  • Keep a held-out set you don't tune against, so you aren't grading your own homework.
  • The docs favor more test cases with automated grading over a few hand-graded ones (develop tests).

No single way of grading covers everything, so mix them:

MethodBest forWatch out for
Code-gradedCrisp truth: a label, a JSON field, a number, a valid schemaCan't judge tone or reasoning
Model-graded (LLM-as-judge)Subjective quality, with a clear rubric and a reason before the scoreThe judge can be wrong. Check it against human labels first
Human reviewHigh stakes, new failure types, calibrating the judgeSlow and costly, so sample it

Mix all three: code where you can, a rubric-guided model where you must, and humans to audit both.

4.3 A/B testing and iterating

  1. Baseline: run the current version on the eval set and save the scores.
  2. Change one thing (the prompt, the model, the retrieval setting or the effort level).
  3. Offline: rerun the whole set. The regression suite must pass. No old case may break.
  4. Online: A/B test on live traffic with metrics you fixed in advance, and let it run long enough to mean something.
  5. Roll out gradually, keep a rollback path, and add the new failures to the eval set.

A prompt change is a production change. Version prompts like code.

4.4 Diagnosing: which layer broke?

When something goes wrong, check the most likely broken layer first, the way you check the plug before the wiring:

SymptomMost likely causeFirst check
Wrong right after a data refresh; model and latency unchangedRetrieval or indexAre the retrieved chunks relevant and current? Same embedding model on both sides?
Right facts in context, but the answer ignores them or has the wrong formatPromptInstructions, examples, output format
Confident claims that no source supportsHallucinationAllow "I don't know", quote first, cite each claim
Fine on easy cases, fails on the hard reasoning onesModel mismatchTry a higher effort level or a more capable model, on the eval set
Slow, or expensive, but correctConfigurationCaching, model tier, batch, effort (4.5)

Look at the trace. The retrieved context tells you if the problem is upstream of the model. The docs' hallucination tactics: let Claude say it doesn't know, ground answers in direct quotes from long documents, and retract any claim it can't back with a quote (reduce hallucinations).

4.5 Optimizing tokens, latency and cost

Each lever below cuts cost or waiting time. Pull it only when its "use when" is true:

LeverWhat it doesUse when
Prompt cachingReuses a stable prefix (tools, system, then messages). Cache reads cost a fraction of normal input. The default lifetime is 5 minutes, and 1 hour costs moreThe same long instructions or documents on many requests. Put static content first
Message Batches50% of standard prices. Most batches finish within 1 hour, and results come within 24 hours at mostNobody's waiting: overnight scoring, backfills, eval runs
Model tieringA smaller model for simple steps, a larger one for hard onesRouting or orchestrator-worker designs (choosing a model)
EffortTrades thoroughness for fewer tokens within one modelOften a better first lever than switching models
Trim contextFewer, better chunks. Trim tool outputLong prompts that are slow and suffer context rot

The caching and batch discounts stack (see pricing). Check that caching works with the usage fields: if both cache_creation_input_tokens and cache_read_input_tokens are 0, nothing was cached. The prompt may be under the minimum cacheable length, which varies by model, so check the current docs.

4.6 Monitoring in production

  • Log per request: prompt and model version, the retrieved chunk IDs, tool calls, tokens, cache usage, latency, and the outcome (including human overrides).
  • Put the eval metrics on a dashboard, and run a sample of live traffic through the graders.
  • Alert on drift: quality score, refusal rate, the rate of escalations to a human, cost per case, and p95 latency.

Worked example

A bank summarizes loan files for its underwriters. After a prompt update, the underwriters say the summaries "feel worse", and the monthly bill has doubled. Answer: first, measure. Rerun the frozen eval set on the old and new prompts. Grade the figures with code (amounts and dates must match the file) and completeness with a rubric-guided model judge, checked against a human-labeled sample. The new prompt drops the covenant section, so roll it back and add those cases to the regression suite. For the cost: move the long, fixed instructions to the front and cache them. Send the overnight backlog through the Batch API. Use a smaller model for the document-type classification step. "Switch to the biggest model" and "ask the underwriters to rate more" skip measurement.

Traps

  • "Judge quality by answer length or exact match on prose." Use a rubric.
  • "Ship it, it looked good on five examples." Use an eval set and a regression suite.
  • "Wrong answers after a re-index, so change the model." Check retrieval first.
  • "Use Batch for the live chat." Batch is for work nobody's waiting on.
  • "Trust the LLM judge without checking it against humans."
