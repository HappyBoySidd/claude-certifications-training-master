Learn architecture through situations you can picture

A customer asks a support representative for a refund. A screen sends the request to your application; Claude helps interpret it, tools retrieve evidence, and trusted application code decides whether a protected action may run. A receipt shows what actually happened. Start with that simple story, then see what changes when something fails.

Plain ↔ technical · MCP / JSON-RPC

Related objective example. Keep the current case's facts and chosen answer separate. For a decision, choose before opening this study help.

In everyday language

An MCP connection advertises capabilities. Your client still has to discover the tool, call it and bring back the result. A project-wide connection is different from one person’s local setup.

Does not establish: Configured server, discovered tool and completed tool execution are three different states. MCP metadata does not grant business authorization.

In technical terms

MCP JSON-RPC tools/list tools/call inputSchema .mcp.json project scope resources/read

Inspect the technical example

Actual MCP tools/call request shape; fictional tool/data, not a Messages tool_use block

{"jsonrpc":"2.0","id":17,"method":"tools/call","params":{"name":"lookup_order","arguments":{"order_id":"O4"}}}

Before this call: discover the available tool and its inputSchema through tools/list.
After it: inspect the actual MCP result/error before adapting it into your model conversation.

Resource content is a different protocol operation:
{"jsonrpc":"2.0","id":3,"method":"resources/read","params":{"uri":"manual://M4/R3"}}
Response excerpt:
{"jsonrpc":"2.0","id":3,"result":{"contents":[{"uri":"manual://M4/R3","mimeType":"text/plain","text":"Approved M4-R3 procedure..."}]}}

Read it as: MCP method and params belong to the client-server protocol. Anthropic Messages uses tool_use/input and tool_result instead; an adapter connects the two boundaries. tools/call invokes a capability; resources/read reads content at a URI. A catalog entry naming the URI is not its text and does not prove the model received it.

Turn a completed course into usable preparation

  1. Trace: close the lesson and reconstruct one request, its data, owners and failure path.
  2. Choose: explain a mechanism, reject its closest alternative, then change one constraint and decide again.
  3. Show evidence: use a paper trace for understanding; an actual API/MCP/CLI lab transcript for execution. Check its prerequisites first. API usage, product access and cloud resources may have separate costs even when learning material is freely accessible.
  4. Return and repair: try the linked simulations or targeted practice, open the exact missed objective, then recall the decision later with flashcards.

A course-completion badge or certificate records course completion. It is distinct from the proctored certification credential and from evidence that you can solve an unfamiliar scenario. Use the full learning journey and readiness limits to judge remaining work. No catalog sweep or fixed number of study hours guarantees a pass.

Hard-mode track

Related technical reference · MCP / JSON-RPC

For people who want more practice than the week plan above. Candidates report scenario judgment (field reports, F: emphasis only). Diagnose the failure before selecting a mechanism: unclear criteria can need better prompting; mandatory authorization needs executable controls; a valid but wrong extracted value needs evidence and semantic validation. No mechanism wins just because it is structural. Hard mode applies that distinction:

  1. Official courses first, from the prep-courses list (Tier 1, checked 2026-10-02): Building with the Claude API, Introduction to MCP, Claude Code in Action. These courses share API concepts, but cloud-platform identity, permissions, endpoints and operational behavior can differ. Use the course companion to choose optional deployment depth; this is not a claim that the courses are interchangeable.
  2. Daily flashcards (Anki import), tagged by task statement.
  3. The 45 hard drills, Domain 1 first. For every wrong option, say why it's wrong.
  4. Decision charts and sequence diagrams: deep-practice.
  5. Before booking: review fresh timed attempts, objective gaps and delayed transfer. Earlier 850+/70% targets were project study heuristics, not official scaled-score predictions; plus the exam guide's sample questions.

Every task statement has its own page: exam objectives.
