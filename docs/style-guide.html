Design style guide

A reference for contributors. Use these tokens and components so every page looks and feels consistent.

1. Principles

  • One idea at a time. Each section or paragraph covers one concept. Split anything that spans two.
  • No outside fonts, scripts or images. Nothing loads from a CDN or third-party domain.
  • 4.5:1 contrast minimum. Every foreground token passes WCAG AA against its background (see swatches below).
  • Works on phones and in print. Responsive layout down to 320 px; the print stylesheet hides navigation.
  • Dark mode built in. All colours are CSS custom properties; dark values swap automatically via the toggle or prefers-color-scheme.
  • No tracking. No cookies, no analytics, no calls to other domains.

3. Type

System sans (--font) — ui-sans-serif, -apple-system, Segoe UI, Roboto, Helvetica Neue, Arial, sans-serif. Body text everywhere.

Serif (--serif) — ui-serif, Iowan Old Style, Palatino Linotype, Georgia, serif. Used for h1 and card headings.

Monospace (--mono) — ui-monospace, SF Mono, Menlo, Consolas, monospace. Inline code and code blocks.

  • Body: 17 px / 1.62 line-height.
  • Lede: 1.15 rem, muted — the one-sentence purpose of a page or section.
  • Eyebrow: 0.78 rem, uppercase, track colour — context label above an h1.
  • H1 uses --serif, clamp 1.9–2.7 rem. H2: 1.45 rem. H3: 1.12 rem. Both sans-serif.

5. Writing style

  • Short sentences. One idea per sentence. If it needs a semicolon, split it into two sentences.
  • Plain words. Write “use” not “utilise”. Write “check” not “verify the accuracy of”.
  • Cite source and tier for every fact. For example: Source: CCAR-F exam guide §3 (Tier 1).
  • No real exam questions. Candidates sign a confidentiality agreement. Simulations and practice items are original.
  • Colleague names withheld until each person agrees. Use “a colleague” as the placeholder.

Lesson shape

  1. Big idea. One sentence — what this lesson proves.
  2. What to know. The exam-weight domain, named sections and key terms.
  3. Worked example. A realistic scenario with a clear right answer and an explanation of why.
  4. Traps. The two or three wrong answers the exam expects you to confuse with the right one.
  5. Try it. One concrete action: paste a prompt, run an API call, or sketch a diagram.
  6. Done when. The observable outcome that confirms you understood the lesson.

6. How to propose a design change

Open an issue through the Contribute page. Include:

  1. What looks or behaves wrong, and which page.
  2. Which token or class is involved (for example --accent or .btn).
  3. A concrete suggestion: a new token value, a class change, or a new component.

Every change goes through the design-system review gate. One fix regenerates all impacted pages from the same token.
