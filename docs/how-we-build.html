Crew workflow — who does what, and which gates every piece of work passes

This is the operating model for building the four Claude certifications (CCAO-F, CCAR-F, CCDV-F, CCAR-P) and the learning site. /crew reads it. Every item in BACKLOG.md runs through one of the pipelines below.

Why the work exists is in CHARTER.md: two intents (Amar passes all four exams; a site for colleagues), one north star, and the rule that Amar's own exam prep wins when the two compete (charter §3). Decisions are logged in DECISIONS.md.

Four rules hold everywhere:

  1. The author never verifies their own work. Each gate is held by a different seat from the one that wrote the item. There's no "same seat, fresh context" exception.
  2. One exam per run. Pipelines never merge exams, and no exam ships at a lower depth than the others.
  3. Tier 1 first. Anthropic's own material is the source. The tiers are in the reference library (in the study workspace).
  4. Study first. Work for the exam Amar is studying now goes before work for a later exam (charter §3).

Current operating contract — 22 October 2026

Git Soma publication within the owner-authorized scope uses standing approval (DECISIONS rows 64, 79, 93 and 94): complete independent review, applicable build/privacy/backlog gates and recorded exceptions, then push without asking again and verify the exact live commit. Never force-push. This does not authorize messages to colleagues, use of names, disclosure of private records or unrelated outward actions.

Use the pipeline definitions below rather than copying their count into editor adapters. The latest applicable owner decision overrides earlier timing holds; the backlog records actual completion. Shared source ownership and checkout identity are documented in the source and release contract.

Runtime capabilities are observed, not assumed. Check available tools and filesystem/network permissions in the current session. Use native named seats when available. A separate agent explicitly assigned an allowed seat must read its exact definition and record that adapter and reviewer identity; it is not a native named runtime. If a required definition or independent reviewer is unavailable, record the missing gate and route a bounded handoff; do not count author self-review as independent. Do not reuse September sandbox grants as current permission evidence.

P9 triggers:

  • The same domain scores under 70% in two sessions or mocks in a row.
  • A simulation decision is missed and the lesson it cites doesn't teach the correct move.
  • Amar notes "the lesson didn't cover this" in the progress log.
  • After an exam, the score report's weakest domain (never the questions).

P9 runs only for the exam in progress or just finished (charter §3). A trigger for a later exam waits as a todo backlog row.

Every dispatch and hand-off carries a contract (the template is in ~/.claude/standards/ops/DISPATCH-CONTRACT.md): mode and seat, goal, inputs, a definition of done, numbered acceptance criteria the receiver will test, guardrails (scope, no outward actions, limits), and a return shape (DONE, INCOMPLETE or BLOCKED, with a pass/fail check per criterion). A seat that can't meet the definition of done returns INCOMPLETE; it never reports partial work as done. Every backlog row states its definition of done before work starts. Stalled or failed seats follow ~/.claude/standards/ops/AGENT-RESILIENCE.md. Permissions are planned up front: before dispatching, the lead lists every step that needs elevation or Amar's OK, bundles them, and asks once at the start (DECISIONS row 46).

3b. Fix loop: what happens when a gate doesn't pass

VerdictNext step
PASSGo to the next gate
PASS WITH FIXESThe author fixes the listed items. The same gate seat rechecks only those items
FAILThe author reworks the item. The same gate seat rechecks the whole item

Rules:

  1. The gate seat never edits the item it's grading. It may suggest exact wording in a finding; the author applies it.
  2. A fix reopens any earlier gate it touches. Changed facts go back through G2 and G4. Changed scope or names go back through G3. Changed exhibits or CSS go back through G8.
  3. At most 2 fix rounds per gate. Round 1 is the first recheck; round 2 is the last.
  4. Stop early if it isn't improving. If round 2 has as many findings as round 1 or more, stop.
  5. Still failing after that: the backlog row goes to blocked with the label [GATE INCOMPLETE — Gn, N findings], and it escalates cpo → exec-reviewer → amar-proxy → Amar. Each seat settles it if it can; only a genuine cost, scope or outward call reaches Amar. The outcome is a row in DECISIONS.md.
  6. Record every round in the backlog row's status, for example G4 r1 FAIL (3) → r2 PASS.
  7. G9 build failures follow the same loop. A second failure of the same check opens P8, so the cause gets fixed, not just the symptom.

5. Where status lives

  • Practice questions surface only in the practice tool (the practice tool (in the study workspace)) and the generated practice sessions. Each one shows an origin pill (Official, Official course, Community, or Project-authored (written by us)), each origin can be filtered on or off, and questions we wrote are never labelled Official. The intake register is the practice tool (in the study workspace).
  • Why, and what winning looks like: CHARTER.md.
  • Decisions and who made them: DECISIONS.md, append only.
  • Work items: BACKLOG.md, one row per item, with the gate it's waiting on and the fix round.
  • Plans: local project plans and operating controls (not published) is the register. Live plans sit in local project plans and operating controls (not published) with a phase tracker; a plan whose rows are all done moves to local project plans and operating controls (not published) with its evidence in the same session. Only the nine core files stay in the project root. local project plans and operating controls (not published) runs before every push.
  • What changed and why: CHANGELOG.md.
  • Exam status: your private progress tracker (not published). Scores: your own notes, which is never published.
  • Site releases: the site repo's CHANGELOG.md and version tags.
